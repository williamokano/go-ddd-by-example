Course · Part 1

The Venue domain model

Pure Go, no database, no HTTP. We build the Venue aggregate test-first: typed IDs, value objects, an entity, the aggregate root, its invariants and its domain events. By the end, internal/venue/domain can express every rule from VEN-1 to VEN-7.

Why start with the domain, and why is it called "domain" and not "app"?

The domain package holds what's true about the business, independent of any software: "a venue can't change its layout once it's active" was true when venues were managed on paper. The application package (Part 2) holds what's true about this program: "load the venue, call Activate, save it, in one transaction". If you put rules in the application layer, they get duplicated across use cases and drift apart. If you put orchestration in the domain, I/O leaks into your most important code.

We start here because the domain depends on nothing. It's the only layer we can build and fully test with zero infrastructure, and everything else depends on it.

1.1 Create the domain package and a typed ID

Goal
Your first red-green-refactor cycle, on the smallest useful value object: VenueID.
Concepts
Value object, typed IDs, Go idioms
Creates
internal/venue/domain/doc.go, venue_id.go, venue_id_test.go
Your turn
  1. Create internal/venue/domain/. Why internal/? Go forbids importing it from outside this module, so it's our private code.
  2. Write doc.go with a package comment explaining in one paragraph what this package is (the Venue Management domain model) and what it must never import.
  3. go get github.com/google/uuid
TDD script
  1. ParseVenueID accepts a valid UUID string and String() round-trips it.
  2. ParseVenueID rejects garbage with ErrInvalidVenueID (check with errors.Is).
  3. ParseVenueID rejects the nil UUID 00000000-…. An ID that identifies nothing isn't an ID.
  4. NewVenueID(uuid.UUID) builds from an already-generated UUID (the application's IDGenerator will call it).
  5. VenueID{}.IsZero() is true and a parsed ID's IsZero() is false.
Pitfall

Don't call uuid.New() inside the domain. Who generates IDs is an application concern (ADR-008), and generating them in the domain makes tests non-deterministic.

Done when

  • 5 tests pass, written in package domain_test. You committed after each green.
Discuss
  • Why type VenueID struct{ value uuid.UUID } rather than type VenueID = string? What bug does it make impossible?
  • Did you hard-code anything to get the first test green? Which test forced you to remove it?

1.2 Value object: Address

Goal
A multi-field, self-validating, immutable value object with table-driven tests.
Rules
VEN-1 (address part)
Creates
address.go, address_test.go, errors.go
TDD script
  1. NewAddress(street, city, country) with valid input returns an address whose getters return the trimmed values.
  2. Table-driven: blank street, blank city, country not two letters → ErrInvalidAddress, with a message that says which field.
  3. The country code is normalised to upper case ("pt" → "PT").
  4. Two addresses built from the same input are == (value equality).

Start errors.go now: one place listing every domain error of the context. Reading that file should feel like reading the rulebook.

Discuss
  • Why does Address have no SetCity? How would a venue "move"? (It gets a new Address value.)
  • Is validating ISO-3166 properly (checking against the real list) a domain concern? What does it cost?

1.3 Value objects: SectionCode and Row

Goal
Practise the "parse, don't validate" habit. After this lesson, raw strings never travel inside the domain.
Rules
VEN-2 (format part), VEN-3 (row part)
Creates
section_code.go, row.go + tests
TDD script
  1. Table: NewSectionCode accepts "ORCH", "bal-l" (→ "BAL-L"), " A1 " (trimmed).
  2. Table: it rejects "", "WAY-TOO-LONG-CODE" (more than 10 chars), "A B" and "ÖRCH".
  3. NewRow(label, seats) rejects a blank label and a seat count < 1.

1.4 Entity: Section

Goal
Your first entity, with a local identity and two shapes (seated / GA).
Concepts
Entity vs value object
Rules
VEN-3, VEN-7 (per section)
Creates
section.go + tests

Two constructors make the two shapes explicit: NewSeatedSection(code, name, rows []Row) and NewGeneralAdmissionSection(code, name, capacity int). Both return (Section, error). The Kind() getter returns Seated or GeneralAdmission.

TDD script
  1. A seated section with rows A(10) and B(12) has Capacity() == 22.
  2. A seated section with zero rows → ErrInvalidSection.
  3. A seated section with duplicate row labels (A, a) → ErrDuplicateRowLabel.
  4. A GA section with capacity 500 has Capacity() == 500 and Rows() empty. Capacity 0 → error.
  5. Rows() returns a copy: appending to or modifying it doesn't change the section.
Discuss
  • Section is an entity, but its identity (SectionCode) is only unique within one venue. Why is that enough? Could anything outside the Venue reference a section by code alone?
  • We used a Kind enum plus two constructors. What would an interface-based design (type Section interface{ Capacity() int }) gain or lose here?

1.5 The aggregate root: registering a Venue

Goal
Create the root and decide what is inside the aggregate.
Concepts
Aggregate & root, creation vs reconstitution
Rules
VEN-1
Creates
venue.go, status.go, venue_test.go, helpers_test.go

The creation function is named after the business act: RegisterVenue(id VenueID, name string, addr Address, now time.Time) (*Venue, error). It returns a pointer because the aggregate is a mutable entity with an identity. Copying it would create two "same" venues that drift apart.

TDD script
  1. Registering returns a venue with that ID, the trimmed name and the address, and a status of Draft.
  2. A blank name, or a name longer than 120 characters → ErrInvalidVenueName.
  3. A zero VenueID or a zero Address → error. (The defensive check against Go's zero values.)
  4. Status.String() returns "draft", "active" and "retired". We'll persist these strings.
Refactor step

Create helpers_test.go with a builder, newDraftVenue(t, opts ...venueOption) *domain.Venue, that hides the irrelevant parts of setup. From now on, each test shows only what it cares about.

1.6 Behaviour through the root: AddSection and capacity

Goal
Enforce invariants that need the whole cluster, and protect the internals.
Rules
VEN-2, VEN-4, VEN-7
TDD script
  1. Adding a section to a draft venue makes it appear in Sections().
  2. Adding a second section with the same code → ErrDuplicateSectionCode (VEN-2), and the venue is unchanged.
  3. Capacity() sums the capacities of all sections (VEN-7).
  4. Sections() returns a copy: mutating the returned slice doesn't change the venue.
  5. (Skip for now and come back in 1.7.) Adding a section to an active venue → ErrVenueNotDraft (VEN-4).
This is why the root is the root

Test 2 can't be written against Section. A section doesn't know its siblings, and only the Venue sees all of them. If Sections() returned the internal slice, a caller could append a duplicate and bypass VEN-2 without calling any method. Test 4 proves the door is locked.

1.7 Lifecycle: Activate and Retire

Goal
Model a state machine as behaviour methods, not a status setter.
Rules
VEN-4, VEN-5, VEN-6
TDD script
  1. Activate(now) on a draft venue with ≥ 1 section → status Active.
  2. Activate without sections → ErrVenueHasNoSections.
  3. Table of illegal transitions: Activate when Active, Activate when Retired, Retire when Draft, Retire when Retired → ErrInvalidVenueTransition.
  4. Retire(now) on an active venue → Retired.
  5. Now go back to the skipped test from 1.6: AddSection on an active venue → ErrVenueNotDraft.
Pitfall

Don't add SetStatus(Status) "for the repository". The repository uses reconstitution (1.9), never mutators. Every public mutator is a way around your invariants.

1.8 Domain events

Goal
The aggregate records what happened. Tests assert on facts, not just on state.
Concepts
Domain event
Creates
events.go (the DomainEvent interface, the Events recorder, and the four event types) + tests

For now the building block (DomainEvent, Events) lives in venue/domain. It moves to the shared kernel in Part 7, when a second context proves the need (ADR-009).

TDD script
  1. RegisterVenue records VenueRegistered{VenueID, Name, At}.
  2. AddSection records SectionAdded{VenueID, Section, At}. That means AddSection now needs now, so update the signature and the tests.
  3. Activate records VenueActivated carrying the full layout, because consumers will need it.
  4. Retire records VenueRetired.
  5. A failed command records nothing.
  6. PullEvents() returns the events in order and empties the list (calling it twice returns nothing the second time).
Discuss
  • Why does the aggregate record events instead of publishing them?
  • Why must a failed command record nothing? Imagine an ErrDuplicateSectionCode that still emitted SectionAdded.

1.9 Reconstitution and version

Goal
Give repositories a way to rebuild a venue from storage without re-running business rules or emitting events.
Concepts
Creation vs reconstitution, optimistic concurrency (ADR-011)

Add RehydrateVenue(VenueState) *Venue, where VenueState is an exported struct with every field (ID, name, address, status, sections, version). Add Version() int to the aggregate. The repository reads everything back through getters.

TDD script
  1. A rehydrated venue exposes exactly the given state through its getters.
  2. A rehydrated venue has no pending events.
  3. A rehydrated active venue still enforces VEN-4 (AddSection fails).
  4. A newly registered venue has Version() == 0.
Discuss
  • VenueState is exported, so any package could call RehydrateVenue with invalid data. How do we keep this honest? (Convention plus the architecture test: only adapters/driven may call it. Add that rule in Part 4.)
  • Who increments the version: the domain or the repository? Why?
