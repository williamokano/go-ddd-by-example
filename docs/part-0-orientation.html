Orientation & setup

Before writing any Go, we make sure we understand the business and that the toolchain works. A programmer on a new project does the same: talk to the domain experts first, then open the editor.

0.1 Event storming on paper

Goal
Discover the domain events, commands, actors and policies yourself before reading the answer.
Concepts
Ubiquitous language, domain events, policies, bounded contexts
Creates
notes/event-storming.md

Read only the first two sections of Chapter 1 ("The business in one paragraph" and "Actors"). Stop before the event-storming diagram.

Your turn
  1. List every domain event you can think of, in the past tense ("SeatsHeld"), in time order. Aim for 20.
  2. For each event, write the command that causes it and the actor who issues it (person, external system, or time).
  3. Find the policies: "whenever X, then Y". (Hint: what happens when a venue closes?)
  4. Draw vertical lines where the language changes. Those are your candidate bounded contexts.
  5. Only now compare with Chapter 1. Write down every difference and whether you think yours or the doc's is better.
Discuss
  • Which word means different things on either side of a line? (Look for "Seat" and "Event".)
  • Which event would hurt the business most if it were lost? That points to the core domain.
  • Is "PaymentCaptured" our event or the payment provider's? What does that tell us about where Payments sits?

Done when

  • You can explain the three main contexts and the core domain in two minutes, without notes.

0.3 Go module, Makefile, linter

Goal
A repo where make test and make lint work, so every later lesson starts green.
Creates
go.mod, Makefile, .golangci.yml, README.md
Your turn
  1. go mod init github.com/williamokano/go-ddd-by-example, and check the go 1.27 line.
  2. Install golangci-lint (Chapter 6 → Tools).
  3. The Makefile already exists with a docs target. Add test and lint. Other targets are added in the lesson that needs them.
  4. Create .golangci.yml (v2 format) with the standard linters plus errorlint, gocritic, revive, testpackage and wrapcheck (with wrapcheck excluded for the domain).
  5. Write a two-line README.md that points to docs/index.html.
Why testpackage?

It pushes tests into package xxx_test, so tests can only use the exported API, the same API other packages use. If you can't test something through the public API, either it isn't behaviour or your API is missing something.

Done when

  • make test prints "no packages to test" without error, and make lint passes.
