7.3 ShowInventory: opening and holding seats

Rules
TKT-1, TKT-2, TKT-3, TKT-5, TKT-12
Creates
internal/ticketing/domain/{seat_ref,inventory,hold,events,errors}.go + tests
TDD script
  1. SeatRef parses "ORCH/A/12" and "FLOOR/GA/0457" and rejects malformed input.
  2. OpenInventory(showID, layoutSnapshot, startsAt, now) enumerates every seat (rows × seat numbers, GA places) with its section price, all Available, and records InventoryOpened.
  3. Hold(holdID, customer, seats, now, ttl) marks the seats Held and records SeatsHeld{expiresAt}.
  4. Holding a seat that's already held or sold → ErrSeatUnavailable, and no seat changes (all or nothing).
  5. 0 seats or more than 8 seats → error. The same seat twice in one request → error.
  6. A second active hold by the same customer → ErrCustomerAlreadyHolding.
  7. Holding after the show's start → ErrSalesClosed.

7.4 Time-based behaviour: release, expire, confirm, sold out, close

Rules
TKT-4, TKT-8, TKT-10, TKT-11
TDD script
  1. ReleaseHold(holdID, customer) frees the seats. Someone else's hold → error.
  2. ExpireHolds(now) frees only holds with expiresAt ≤ now, and records HoldExpired for each. A fixed clock means no sleeping.
  3. ConfirmHold(holdID, orderID, now) on a valid hold → the seats are Sold, and SeatsSold{orderID, seats} is recorded.
  4. ConfirmHold on an expired hold, even one not yet swept, → ErrHoldExpired, and the seats are not sold.
  5. Confirming the same order twice is a no-op (idempotent, because the saga may redeliver).
  6. Selling the last available seat records InventorySoldOut exactly once.
  7. Close(now) releases all holds and rejects any new hold.

7.5 Inventory application, persistence, HTTP, and reacting to Show

Creates
OpenInventory (from show.published.v1), HoldSeats, ReleaseHold handlers; Postgres repo (ticketing.inventories, ticketing.seats, ticketing.holds); HTTP POST /shows/{id}/holds, DELETE /holds/{id}, GET /shows/{id}/seats; a consumer for show.events
TDD script (highlights)
  1. HTTP: POST /shows/{id}/holds takes {"customerId", "seats"} and DELETE /holds/{id} takes {"customerId"} in its body (no login; see chapter 1). A missing customer id → 422; someone else's hold → 403.
  2. Receiving show.published.v1 twice opens the inventory once (TKT-1).
  3. HoldSeats retries on ErrConcurrentModification (up to 3 times) and then gives up with a 409.
  4. The repository writes only changed seats, not all 50k. Track dirty seats in the aggregate, or diff them in the adapter. Discuss which.
  5. GET /shows/{id}/seats is a query that reads the seats table directly, with no aggregate load.

7.7 The Order aggregate and the payment port

Rules
TKT-6, TKT-7
Concepts
A driven port to an external system as an ACL; a spy fake
Creates
domain/order.go; the application.PaymentGateway port (Charge(ctx, orderID, amount) (PaymentRef, error), Refund(ctx, ref, amount) error); adapters/driven/payment/fakegateway
TDD script
  1. PlaceOrder(orderID, customer, contactEmail, hold view, prices, now): the total is the sum of the lines; mixed currencies → error; the order is Pending and records OrderPlaced.
  2. ContactEmail is a value object: trimmed and lower-cased, and a malformed address → error before any order exists (TKT-6).
  3. Transition table for Pending → Paid / PaymentFailed, Paid → Fulfilled / Refunded, Fulfilled → Refunded, plus the illegal ones.
  4. Fake gateway modes: approve, decline, delay. It records calls so tests can assert "Refund was called for order X".
The payment port is an Anti-Corruption Layer

Real providers speak their own language (intents, captures, webhooks). The port speaks ours: Charge and Refund. A future Stripe adapter does the translation, and the domain never learns that word.

7.8 Checkout and the saga

Rules
TKT-8, TKT-9; ADR-010
Creates
The Checkout use case (place + charge); the Ticket aggregate; saga handlers ConfirmHold, IssueTickets, RefundOrder; a consumer on ticketing.internal

Follow the diagram in Chapter 4 → The checkout saga.

TDD script
  1. Checkout (with fakes): approved payment → order Paid, OrderPaid saved. Declined → PaymentFailed, and the hold stays (the customer can retry).
  2. ConfirmHold handler: on OrderPaid, the inventory confirms. Redelivery is a no-op.
  3. IssueTickets handler: on SeatsSold, one ticket per seat with unique codes (TKT-9), and the order becomes Fulfilled. Redelivery issues no duplicates. How do you detect that? (A deterministic ticket ID derived from order + seat, or a uniqueness constraint.)
  4. RefundOrder handler: on HoldConfirmationFailed, the gateway refunds and the order becomes Refunded. This is the compensation.
  5. HTTP: POST /orders takes {"holdId", "customerId", "contactEmail"}, all typed by the customer. A missing or malformed field → 422; a hold that isn't this customer's → 403 (TKT-6).
  6. The S1 outer-loop test goes green.

7.10 Closing the loops with Show

Rules
TKT-10, TKT-11, SHW-8
Creates
ticketing/contracts with golden tests; the outbox translation; Show's consumer for ticketing.events; Ticketing's handler for show.cancelled.v1
TDD script
  1. InventorySoldOut → ticketing.inventory_sold_out.v1 → Show is SoldOut (S4, e2e).
  2. show.cancelled.v1 → the inventory closes, every ticket is voided, and every Paid/Fulfilled order is refunded. Each of those is its own transaction, driven by events.
  3. show.cancelled.v1 for a show that was cancelled while still Draft (so no inventory exists) is a harmless no-op, not a DLQ entry.
  4. Show side: inventory_sold_out arriving for a show that has already been cancelled. ticketing.events and show.events are different topics, so nothing orders them. MarkSoldOut on a terminal show must be ignored, not rejected.
