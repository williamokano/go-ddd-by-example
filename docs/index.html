Learning DDD, Hexagonal Architecture and TDD by building a ticketing platform in Go

This is the course map. You'll build Stagehand one piece at a time, the way a working programmer would. You'll read a little theory, write a failing test, make it pass, refactor, and then talk about why it went where it went.

What we are building

Stagehand sells tickets for shows held at venues. It has three main business areas (bounded contexts) plus a small generic one:

Venue Management supporting

Venues, their sections and their seats. A venue manager registers a venue, lays out its sections, activates it, and eventually retires it.

Show Scheduling supporting

A promoter drafts a show at an active venue, sets a price for each section, publishes it, and can cancel it. Shows can't overlap at the same venue.

Ticketing core

Customers hold seats for a few minutes, check out, pay, and get tickets. A seat is never sold twice. This is where the business makes its money, so it gets the richest model.

Notifications generic

Reacts to events and "sends" emails (it logs them). It shows that not everything needs a rich domain model.

The contexts live in one Go module (a modular monolith). Each owns its own Postgres schema, and they talk to each other only through integration events on Kafka. Each event is written with the transactional outbox pattern, so we never lose one. We get the discipline of microservices without the operational cost, and splitting a context out later would be a deployment change, not a rewrite.

How the course works

Read Key terms in 10 minutes first. It defines every word the course uses: driving/driven ports and adapters, value objects, aggregates and the rest. After that, there are two kinds of pages:

  • Reference (chapters 1–7). The domain description, the concepts, the architecture rules, the testing strategy, the infrastructure and the decision log. Read chapter 1 before Part 0, then come back to the others when a lesson points you there.
  • Course (Parts 0–9). Step-by-step lessons. Each lesson has a goal, the concepts it introduces, the files you'll create, a TDD script (the ordered list of tests to write), a "done when" checklist and discussion questions. Tick "done" on a lesson to track your progress. Progress is saved in this browser only.

The teaching protocol (what happens in a session)

  1. We open the next unfinished lesson. I explain the concept and the why, using our domain as the example.
  2. I give you a concrete instruction, e.g. "create internal/venue/domain/venue_id.go".
  3. You write the failing test first. I review it: does it describe behaviour, is it named in the ubiquitous language?
  4. You make it pass with the simplest code. Then we refactor together.
  5. I don't write the production code for you unless you ask. I give hints, ask questions, and review your diffs.
  6. At the end of each lesson we run the "done when" checks, answer the discussion questions, and commit.

Why this order?

We go inside-out first. We start at the domain (pure Go, no database, no HTTP) because that's what DDD is about, and because it's the easiest place to learn TDD: no mocks, no setup, instant tests. Only once the model works do we add the ring around it (use cases), then the adapters (Postgres, HTTP, Kafka).

The Venue context goes first because it's the simplest and everything else depends on it. Show repeats the same pattern faster and adds cross-context events. Ticketing, the hard part, comes last, when you already know the moves. From Part 6 on we switch to outside-in (double-loop) TDD: an acceptance test first, then inside-out to make it pass.

Prerequisites

  • Go 1.27 (go version), Docker with the Compose plugin, make.
  • Installed during Part 0: sqlc, golangci-lint (goose is already installed).
  • Comfortable Go basics: structs, methods, interfaces, errors, context, table-driven tests.

Viewing these docs

Opening docs/index.html directly works. Serving the folder over HTTP is nicer, though: one stable URL, and lesson progress that survives across browsers on the same address.

make docs                                             # http://localhost:8000
# or, without make:
python3 -m http.server 8000 --bind 127.0.0.1 --directory docs

Use another port with make docs DOCS_PORT=9000. Lesson progress is stored per address, so file:// and http://localhost:8000 track it separately.

Resuming in a new session

The repo's CLAUDE.md tells Claude to act as your tutor for this course, and tasks/todo.md records the lesson we're on. Start a session with something like "Let's continue the course". Claude reads both files, checks the code that exists, and picks up at the next unchecked lesson.
