Reference · Chapter 1

The domain

This chapter is the specification: what the business does, the words it uses, where the boundaries are, and the rules the code must keep. Every test we write traces back to a rule on this page, using its rule ID (e.g. VEN-3).

The business in one paragraph

Stagehand is a ticketing platform. Venue managers register venues (theatres, arenas, clubs) and describe their layout: sections, rows and seats. Promoters schedule shows at those venues and set a price for each section. Once a show is published, customers pick seats. The seats are held for them for a few minutes while they check out. If payment succeeds the seats are sold and tickets are issued; if the hold runs out first, the seats go back on sale. Things go wrong in the real world: shows get cancelled and venues close. When that happens, customers are refunded and told about it.

Actors

ActorGoals
Venue ManagerRegister venues, describe the seating layout, activate and retire venues.
PromoterDraft shows, price them, publish them for sale, cancel them.
CustomerBrowse shows, hold seats, check out, receive tickets, get refunds.
Payment Provider (external system)Charge and refund money. We don't own it, we only talk to it.
The Clock (time-based actor)Holds expire and shows end because time passes. Time is an actor too, and we treat it like one.

Why start from events?

Events are the facts the business already talks about ("the show sold out", "the hold expired"), so domain experts can follow them without knowing anything about software. The places where events change hands between groups of people show you where the bounded contexts are. Commands, aggregates and policies come next, attached to the events.

Bounded contexts and their languages

A bounded context is a part of the solution space: a boundary inside which every word has exactly one meaning, and one model applies. The same word can mean different things in different contexts. That isn't a bug; it's the reason the boundaries exist.

The word "Seat" means three different things
  • Venue: a physical place. Section A, row 3, seat 12, wheelchair accessible. It has no price and no status.
  • Show: it barely exists. Show cares about sections and their prices, not individual seats.
  • Ticketing: a sellable unit for one show, with a state (Available / Held / Sold) and a price.

One shared Seat struct covering all three would be a mess of optional fields owned by nobody. Each context keeps its own model.

We don't say "Event" for the business concept

The business sometimes says "event" for a concert. We already use event to mean domain event, so the ubiquitous language uses Show for the concert. Settling this on day one avoids a whole class of confusing conversations and code.

Aggregates, rules and events per context

Rule IDs are referenced from tests (e.g. func TestVenue_AddSection_RejectsDuplicateCode_VEN2(t *testing.T), or just a comment). That keeps the spec and the tests linked.

Venue Management

Aggregate: Venue (root). It contains Section entities. A section contains its rows as value objects, and seats are derived from the rows.

Value objects: VenueID, Address, SectionCode, Row, SectionKind, VenueStatus.

IDRule (invariant or policy)
VEN-1A venue has a non-blank name (≤ 120 chars) and a valid address (street, city, country code ISO-3166 alpha-2).
VEN-2Section codes are unique within a venue (case-insensitive, stored upper-case, 1–10 chars [A-Z0-9-]).
VEN-3A seated section has ≥ 1 row, each row ≥ 1 seat, and row labels are unique within the section. A GA section has a capacity ≥ 1 and no rows.
VEN-4The layout (sections) can only change while the venue is Draft.
VEN-5A venue can be activated only from Draft and only if it has ≥ 1 section.
VEN-6A venue can be retired only when Active. Retired is terminal.
VEN-7Capacity = the number of seats in seated sections + the capacity of GA sections.

Commands → domain events: RegisterVenue → VenueRegistered · AddSection → SectionAdded · ActivateVenue → VenueActivated · RetireVenue → VenueRetired.

Publishes: venue.activated.v1 (venue id, name, full layout: each section with code, kind, and rows (label + seat count) or GA capacity) · venue.retired.v1 (venue id, retired at).

Show Scheduling

Aggregate: Show (root). Value objects: ShowID, VenueID (Show's own type), PromoterID, Schedule, Money, PriceList, CancellationReason, ShowStatus. It references the venue by ID only. Read model: VenueLayout (a local projection of venue facts).

IDRule
SHW-1Title is non-blank (≤ 200 chars). A show is drafted only for a venue that is Active according to the local VenueLayout.
SHW-2Schedule: doorsOpen ≤ startsAt < endsAt; duration ≤ 12h; startsAt is in the future when drafted, rescheduled or published.
SHW-3Two non-cancelled shows at the same venue cannot overlap in time (from doorsOpen to endsAt). This is a cross-aggregate rule, so it lives in a domain service.
SHW-4The price list has a strictly positive price for every section of the venue, and nothing else. All prices use one currency.
SHW-5Only a Draft show can be priced or rescheduled. Publishing requires a complete price list (SHW-4).
SHW-6Draft, Published or SoldOut shows can be cancelled. Cancelled and Completed are terminal.
SHW-7When a venue is retired, every non-terminal show at it whose start is in the future is cancelled with reason venue_retired. (Policy reacting to another context.)
SHW-8When Ticketing reports the inventory is sold out, a Published show becomes SoldOut. Receiving the same fact twice, or receiving it for a Cancelled/Completed show, is a no-op.

Publishes: show.published.v1 (show id, venue id, schedule, and each section with code, kind, rows or GA capacity, and price) · show.cancelled.v1 (show id, reason). Consumes: venue.activated.v1, venue.retired.v1, ticketing.inventory_sold_out.v1.

Design note

show.published.v1 carries a snapshot of the sections and prices, so Ticketing never has to ask Venue or Show anything. Because of that snapshot, if the venue's layout changed later, already-published shows keep selling the layout they were published with. That's the business rule we want.

Ticketing (core)

Aggregates:

  • ShowInventory (root): per show, all seat states plus the active Holds (entities inside it). It's the consistency boundary for "never sell a seat twice".
  • Order (root): one checkout of one hold. Contains OrderLine value objects.
  • Ticket (root): one per sold seat. Small and independent, so it can be voided or checked in without locking anything else.

Value objects: ShowID, CustomerID, HoldID, OrderID, TicketID, SeatRef, SeatState, Money (shared kernel), OrderLine, PaymentRef, TicketCode.

IDRule
TKT-1An inventory is opened once per published show, from the snapshot in show.published.v1. Opening it twice is a no-op (idempotent).
TKT-2A hold contains 1–8 seats, all Available at the moment of holding. Otherwise the whole hold is rejected (all or nothing).
TKT-3A customer has at most one active hold per show.
TKT-4A hold expires at heldAt + 10 min. Expired holds release their seats. Expiry is evaluated against a time passed in, never time.Now() inside the domain.
TKT-5A seat is never Sold twice and never held by two holds. (The core invariant.)
TKT-6An order is placed only for a non-expired hold owned by the same customer. Its total = the sum of the line prices, in one currency.
TKT-7Order lifecycle: Pending → Paid → Fulfilled, or Pending → PaymentFailed, or Paid → Refunded. Fulfilled → Refunded happens when the show is cancelled.
TKT-8Confirming a hold for a paid order sells its seats. If the hold has expired or been released by then, confirmation fails and the order must be refunded (compensation).
TKT-9One ticket is issued per sold seat. Each ticket code is unique.
TKT-10When every seat is Sold, the inventory raises InventorySoldOut exactly once.
TKT-11When a show is cancelled, the inventory closes (no new holds; active holds are released), all its tickets are voided, and every Paid/Fulfilled order is refunded.
TKT-12No new holds on a closed inventory or after the show's start time.

Publishes: ticketing.inventory_sold_out.v1, ticketing.tickets_issued.v1, ticketing.order_refunded.v1. Consumes: show.published.v1, show.cancelled.v1.

Notifications (generic)

No aggregates. A handler per integration event formats a message and sends it through an EmailSender port; the adapter just logs it. It's here to show that a transaction script is the right tool for a generic subdomain.

Key scenarios (acceptance criteria)

These become the end-to-end tests in Part 8. Every arrow that crosses contexts is a Kafka message.

S1 — Happy purchase

Given an active venue and a published show → a customer holds 2 seats → places an order → payment succeeds → the seats are sold → 2 tickets are issued → a "tickets issued" email is logged.

S2 — Hold expires

Given a hold → 10 minutes pass without checkout → the seats become Available again and another customer can hold them.

S3 — Late payment (compensation)

Given a hold that expires while payment is in flight → payment succeeds → confirmation fails (TKT-8) → the order is refunded → a refund email is logged. The seat is not sold twice.

S4 — Sold out

Given a show with 3 seats → all 3 are sold → Ticketing publishes sold-out → the show becomes SoldOut.

S5 — Venue retires (the full cascade)

Given a venue with a future published show and a fulfilled order → the venue is retired → the show is cancelled → the inventory closes, tickets are voided, the order is refunded → a refund email is logged.

S6 — Race for the last seat

Given 1 available seat and 50 concurrent hold requests → exactly 1 succeeds and 49 get "seat unavailable".

Out of scope

  • Authentication and authorisation. Actor IDs come from headers.
  • A real payment provider, real email, PDFs and QR codes.
  • Dynamic pricing, discounts, fees and taxes. (A stretch goal could add fees as a domain service.)
  • A frontend. We drive everything over HTTP with curl / .http files.
