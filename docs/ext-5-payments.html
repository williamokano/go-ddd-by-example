Payments: modelling a messy outside world

In Part 7 payment was a two-method port with a fake behind it. Real payments are a whole subdomain: authorize, capture, void, refund, declines, unknown outcomes, webhooks, disputes and reconciliation. You'll grow that port into a Payments bounded context, put a real Stripe sandbox adapter behind it, and then add features to the existing domain: customer refunds, chargebacks, and a small Denylist context that stops a charged-back customer from buying again. The lesson isn't Stripe. It's keeping Stripe out of your language.

What changes in the main course's story

Chapter 1 classifies Payments as generic: buy it, here a fake adapter, and lists a real provider as a non-goal. We still buy the card processing, but the part that decides what a payment is, what states it has, and what we do on a dispute is ours, and it's rich enough to deserve its own context. This is recorded as ADR-E10; the chapter is left as is.

Rules

IdRule
PAY-1A payment is created for one order attempt, in one currency, for one amount > 0. Creating it twice for the same order and attempt is idempotent (returns the existing payment). A declined payment is final; the customer's retry is a new attempt, so a new payment.
PAY-2Lifecycle: Initiated → (AuthenticationRequired →) Authorized → Captured; or Initiated/Authorized → Declined/Voided. From Captured, refunds lead to PartiallyRefunded and Refunded (E5.2), and an accepted dispute makes the payment ChargedBack (E5.10); nothing else leaves Captured.
PAY-3Capture amount ≤ authorized amount. (Capturing less releases the rest; capturing more is rejected.)
PAY-4Σ successful and pending refunds ≤ captured amount. (The core invariant of this context, the analogue of TKT-5.)
PAY-5Every provider call carries an idempotency key derived from the payment id, the operation, and the attempt number. A timeout is an unknown outcome, never a decline, and is resolved by re-asking with the same key or by reconciliation.
PAY-6A provider notification is applied at most once (de-duplicated by provider event id), may arrive out of order, and may arrive for a payment we haven't finished saving.
PAY-7An authorization that wasn't captured within the provider's window (default 7 days for cards, configurable) is treated as expired and moved to Voided by reconciliation.
PAY-8For now, every dispute is accepted on arrival: we tell the provider we accept it and never submit evidence. An accepted dispute is final, the payment becomes ChargedBack, and the disputed amount can no longer be refunded (PAY-4 extended). Defending disputes is the E5.14 stretch.
PAY-9An authorization is refused, without calling the provider's authorize endpoint, when the payment method's fingerprint is denylisted (DNY-4). The decline reason is the generic PaymentMethodNotAccepted.

E5.2 Refunds inside the aggregate (PAY-4)

Goal
Model refunds so "never refund more than was captured" can't be broken, even with concurrent refund requests.
Rules
PAY-4
Concepts
Aggregate boundary = invariant boundary (chapter 2), ADR-011
TDD script
  1. RequestRefund(refundID, amount, reason, now) on a Captured payment adds a Refund entity in Requested; on any other state → error.
  2. Two refunds of 60 on a captured 100 → the second fails with ErrRefundExceedsCaptured (counts pending and succeeded ones).
  3. MarkRefundSucceeded / MarkRefundFailed: a failed refund frees its amount for another attempt.
  4. A fully refunded payment becomes Refunded; partial leaves it PartiallyRefunded. Both still allow further refunds up to the limit.
  5. RequestRefund with an existing refund id and the same amount is idempotent (the caller retried).
Why an entity inside Payment, but Dispute a separate aggregate?

PAY-4 is a true invariant across all refunds of a payment: it must hold at every instant, so they live in one consistency boundary (ADR-E13). A dispute has its own lifecycle, deadline and actors, and is driven by an external party on its own schedule. It points at the payment by id and affects it eventually, through an event. Compare this with ADR-005 and decide where you'd draw the line if refunds were also initiated by a third party.

Discuss

Under heavy concurrent refund requests (support clicking twice), which mechanism guarantees PAY-4: the aggregate, the optimistic version, or the database? Write the test that proves it, as you did for TKT-5 in 7.6.

E5.3 The PaymentProvider port, normalized notifications and a scriptable fake

Goal
Define what Payments needs from any processor, in our words, then build a fake you can script.
Rules
PAY-5, PAY-6
Creates
payments/application/{ports,notification}.go, adapters/driven/fakeprovider
// A design to react to, not to copy. Note: no Stripe word anywhere.
type PaymentProvider interface {
    Authorize(ctx context.Context, r AuthorizeRequest) (AuthorizeResult, error)
    Capture(ctx context.Context, r CaptureRequest) (CaptureResult, error)
    Void(ctx context.Context, r VoidRequest) error
    Refund(ctx context.Context, r RefundRequest) (RefundResult, error)
    AcceptDispute(ctx context.Context, r AcceptDisputeRequest) error
    // A stable, provider-scoped fingerprint of the card behind a one-time
    // token, plus display hints (brand, last 4). Used by E5.12 and E6.
    DescribePaymentMethod(ctx context.Context, t PaymentMethodToken) (
        PaymentMethodInfo, error)
}
// Every request carries an AttemptKey. Every result is a sealed set:
//   Authorized | Declined{Reason} | AuthenticationRequired | Pending.
// Transport failures are a distinct error (ErrUnknownOutcome),
// never mapped to Declined.

// Provider-initiated facts, already translated by the adapter:
type ProviderNotification interface{ isNotification() }
// AuthorizationConfirmed, CaptureSettled, RefundSettled, RefundFailed,
// DisputeOpened, DisputeClosed, ...
TDD script (the contract suite)
  1. Authorize twice with the same AttemptKey → the same result, no second authorization. (The suite will run against the fake now and against Stripe in E5.7.)
  2. The fake supports a scripted card number-like trigger (e.g. a token tok_decline_funds) → Declined/InsufficientFunds; tok_timeout → ErrUnknownOutcome but the authorization really happened, so that a later retry with the same key returns the authorized result. (That's exactly how real timeouts behave, and exactly what naïve code gets wrong.)
  3. The fake can later emit notifications (settlement, a dispute) through a channel the webhook adapter also feeds, so you can test the whole flow without a network.
  4. Capture more than authorized → ErrCaptureExceedsAuthorization, from the fake too, because the provider enforces it as well.
Pitfall: the leaky port

If a port method takes map[string]any "metadata", returns the provider's status string, or exposes the provider's error type, the vendor has crossed the wall. Review the port for these three.

E5.4 Use cases with idempotency and unknown outcomes

Goal
Authorize, Capture, Void and Refund as use cases that survive timeouts and retries.
Rules
PAY-5
TDD script
  1. AuthorizePayment: creates or loads the Payment (PAY-1), saves it first, then calls the provider with a key derived from paymentID/authorize/attempt, then applies the result and saves again. Why save before the call?
  2. Provider returns Declined → payment Declined, PaymentDeclined{reason} recorded. The customer may retry: a new attempt, a new key.
  3. ErrUnknownOutcome → the payment stays Initiated with an "attempt in flight" marker and the use case returns a distinct "pending" result. A retry with the same key then resolves it (fake scripts it).
  4. CapturePayment when the capture call times out → unknown outcome again; the reconciler (E5.13) will settle it.
  5. RefundPayment → RequestRefund on the aggregate (PAY-4 checked before any provider call), then the provider call, then success/failure applied.
  6. An optimistic-concurrency conflict on save retries the use case, but never the provider call without its key.
Discuss

"Save, call, save again" is a tiny saga with the database and the provider as participants. Where could you crash, and what state would the next process find? Walk each point.

If Payments is ever extracted, Client becomes an HTTP/gRPC client and nothing in Ticketing changes.

In Ticketing, void already means invalidating a ticket (chapter 1). In Payments, it means releasing an authorization. Both are right inside their own context, which is the point of bounded contexts, but Ticketing's port must speak Ticketing's language. That's why its method is CancelAuthorization, and the ACL adapter translates it into Payments' Void.

E5.8 Webhooks: the provider calls us

Goal
A driving adapter that verifies, translates and applies provider notifications exactly once.
Rules
PAY-6
Creates
payments/adapters/driving/webhook, ApplyProviderNotification use case; reuses 8.4's payments.inbox with the provider's event id as event_id
TDD script
  1. A request with a bad or missing signature → 400, nothing applied. (Verification happens on the raw body, before parsing.)
  2. A valid request is translated into a ProviderNotification by the Stripe-specific code; the use case never sees JSON. Unknown event types are acknowledged (2xx) and ignored, so the provider doesn't retry them forever.
  3. The same event delivered twice → applied once (inbox keyed by provider event id, in the same transaction as the state change, the idea from 8.4).
  4. An out-of-order case: CaptureSettled arrives while the payment is still Authorized or even unknown locally → handled by PAY-2's tolerant transitions or parked and retried (decide, test, document).
  5. A notification for a payment we've never heard of → recorded, not an error, plus a metric (E3).
  6. The handler returns 2xx only after commit; any failure returns 5xx so the provider retries.
Your turn: try it for real
  1. Use the Stripe CLI's stripe listen --forward-to localhost:8080/webhooks/stripe to deliver sandbox events to your running app.
  2. Make the fake provider also deliver through the same endpoint shape so e2e tests exercise the real adapter path without Stripe.
Pitfall

Webhooks are advice from the outside, not the source of truth. When in doubt about a payment's state, ask the provider (E5.13) rather than trusting arrival order.

E5.10 Feature: chargebacks, accepted on arrival

Goal
Model something that happens to us on someone else's schedule, with the simplest policy that's safe: accept every dispute, cancel the tickets, and remember who did it.
Rules
PAY-8, TKT-17 (new); ADR-E16
Creates
payments/domain/dispute*.go, webhook mappings for disputes, AcceptDisputeOnArrival policy, Ticketing's reaction, ticketing.order_charged_back.v1
IdRule
TKT-17When Payments reports a chargeback for an order, the order becomes ChargedBack and its tickets are voided for good (a gate scan must fail, 9.2). Nothing is refunded: the bank has already taken the money back. Ticketing publishes ticketing.order_charged_back.v1 with the order, the customer, the order's contact email and the payment method's fingerprint.
TDD script
  1. OpenDispute(disputeID, paymentID, amount, reasonCode, respondBy, now) only for a captured payment (possibly partly or fully refunded); the amount can't exceed what was captured. Records DisputeOpened.
  2. Accept(now) moves Open → Accepted exactly once; a second call is a no-op (PAY-6). Won/Lost states exist in the type but nothing produces them yet (that's E5.14).
  3. Policy AcceptDisputeOnArrival (an application-level reaction to DisputeOpened): calls PaymentProvider.AcceptDispute with an idempotency key, then accepts the dispute and marks the payment ChargedBack. A provider timeout leaves the dispute Open for the reconciler (E5.13).
  4. payments.dispute_accepted.v1 carries the orderRef, the amount and the payment method's fingerprint.
  5. Ticketing consumes it (TKT-17): order ChargedBack, tickets voided, no call to RefundOrder. Write that test explicitly: refunding a charged-back order would lose the money twice.
  6. A chargeback on an order that was already refunded (E5.9) still voids nothing new and refunds nothing; it's recorded, and staff are alerted, because the customer got their money back twice.

E5.11 The Denylist context

Goal
A small, generic domain that answers one question: "is any of these identifiers blocked?", for whatever kinds of identifier we decide to block.
Rules
DNY-1 … DNY-5
Concepts
Value objects with normalisation, a small aggregate, generic subdomain
Creates
internal/denylist/{domain,application,contracts}, db/migrations/0000N_denylist.sql, Postgres adapter
IdRule
DNY-1An identifier is a (kind, value) pair. Kinds are a closed list that grows on purpose: customer, email, payment_method (a provider-scoped card fingerprint, never a token or a number); E6 may add device. Each kind normalises its value (emails are trimmed and lower-cased), and an unknown kind is rejected.
DNY-2There is at most one active entry per identifier. Blocking an already blocked identifier is idempotent and only adds the new reason and source (for example, a second chargeback).
DNY-3Every entry records why (chargeback, fraud_confirmed, manual), its source reference (the dispute id), when, and who (a user or system:chargebacks). Entries are never deleted: lifting one records who lifted it, when and why, and requires denylist:manage.
DNY-4A check takes a set of identifiers and says blocked if any of them has an active entry. The answer names the matched kinds for staff and audit; the customer only ever sees a generic refusal.
DNY-5The list holds no raw personal data it doesn't need: emails are stored as a keyed hash (HMAC with a secret from config), so lookups still work but the table isn't a list of addresses.
TDD script
  1. NewIdentifier(kind, value): " Ana@Example.com " and "ana@example.com" are the same email identifier; an empty value or unknown kind → error.
  2. Block(identifier, reason, source, by, now) on a new identifier creates an active Entry and records IdentifierBlocked; on an active one it adds the reason/source and records nothing else (DNY-2).
  3. Lift(by, why, now) deactivates the entry and records IdentifierLifted; lifting twice is a no-op; blocking a lifted identifier reactivates it with the new reason, keeping the history.
  4. Application: Check(identifiers) returns Verdict{Blocked, MatchedKinds}, reading active entries only (a query, as in 2.5: no aggregate load).
  5. The email hasher is a driven port; the fake hashes deterministically so tests stay readable.
  6. Publish the check as an Open Host Service, denylist/contracts.Client.Check(...), with DTOs only, exactly like Payments in E5.5.
Discuss

Should a.n.a+tickets@gmail.com match ana@gmail.com? Provider-specific normalisation catches evasion but can block innocent people. Which context owns that rule, and where does a mistake get corrected?

E5.12 Block on chargeback, enforce at purchase

Goal
A charged-back customer can't buy anything again: not with the same account, not with the same email on a new account, and not with the same card on any account.
Rules
TKT-19 (new), PAY-9, DNY-4
Touches
Denylist (a policy, and a projection of Identity's events), Ticketing (HoldSeats, Checkout), Payments (AuthorizePayment), Identity's published contract (E2)
IdRule
TKT-19A customer whose account is denylisted can't hold seats or place orders, and no order can be placed with a denylisted contact email. The refusal is the same generic error for every reason, and it happens before any seat is touched.

TDD script (outside-in)
  1. Acceptance (red): a customer buys, the fake provider opens a dispute → the order is ChargedBack, tickets are void, and then: (a) the same account can't hold seats; (b) a new account can't check out with the same contact email, and can't even hold seats if its account email is the blocked one; (c) a different, clean account paying with the same card is declined with PaymentMethodNotAccepted; (d) a clean account with a different card buys normally.
  2. Policy BlockOnChargeback: one event → entries for the customer, the order's contact email, the customer's account email (when the projection knows it; often the same value, so DNY-2 collapses them) and the card, each with reason chargeback and the dispute as source. Redelivery adds nothing (DNY-2 + inbox).
  3. Projection: Denylist keeps customerId → account email hash from Identity's events (publish identity.user_registered.v1 and identity.user_email_changed.v1 from E2 if you haven't). A check for customer:X also checks X's account email, which is how a fresh account with the blocked address is caught at HoldSeats.
  4. Ticketing: HoldSeats checks {customer}; Checkout checks {customer, email: contactEmail}. Both run before touching the inventory or the order; blocked → ErrPurchaseNotAllowed → 403 with a generic body. With E2, the customer id comes from the principal, so it can't be spoofed.
  5. Payments: AuthorizePayment calls DescribePaymentMethod (the fake returns a fingerprint per test token, Stripe returns the card's fingerprint), checks it, and refuses without authorizing (PAY-9). The fingerprint is stored on the payment, which is where E5.10's event gets it.
  6. Staff with denylist:manage can lift an entry through DELETE /denylist/{kind}/{value} with a mandatory reason; with E4, both the block and the lift are in the audit trail.
  7. The denylist being unavailable fails the purchase (fail closed): it's our own database, so if it's down, so is checkout. Contrast with the fraud vendor in E6.4.
Why a context of its own, and why not block the token?

Blocking is a policy many contexts will use (chargebacks today, confirmed fraud in E6, a staff decision tomorrow) about identifiers that belong to different contexts (Identity owns account emails, Ticketing owns customers and contact emails, Payments owns card fingerprints). Putting the list in any one of them would make the others depend on its model. A tiny generic context with a published Check keeps the dependency pointing the right way (ADR-E17). The token is useless to block: the browser gets a new one every time. The provider's card fingerprint is stable across tokens for the same card, so that's the identifier.

Discuss

A family shares one card; one member charges back. Everyone is now blocked. Is that the business you want? What would you change (expiry, staff review, blocking only the card), and in which rule?

E5.13 Reconciliation and failure drills

Goal
Assume every message and every call can be lost, duplicated or late, and build the net underneath.
Rules
PAY-5, PAY-7
Your turn
  1. A reconcile scheduler (a driving adapter) finds payments stuck in Initiated with an attempt in flight, Authorized past their window, or disputes still Open because accepting them timed out, and asks the provider for the truth, re-using the original idempotency key for the operations that support it. It applies the answer through the same use case the webhook uses.
  2. Expose a payments_stuck{state} gauge and the age of the oldest stuck payment (E3). A reconciler that never finds anything is the goal; a graph that shows it is the proof.
  3. Drills with the fake provider (put them in a table): (a) provider times out after succeeding; (b) provider fails before succeeding; (c) webhook arrives before the API response; (d) webhook delivered five times; (e) provider down for ten minutes; (f) capture succeeds but our save fails. For each write down the state of the system at every step and the test that proves it converges.
  4. Finish: run the full S1–S6 acceptance suite plus the new refund, chargeback and denylist scenarios against the fake, then run S1 by hand against the Stripe sandbox with the CLI forwarding webhooks, and watch every event in Kafka UI.

E5.14 Stretch: defend disputes instead of accepting them

Goal
Replace "accept on arrival" with a real defence, for the learner to design and build.
Concepts
Process ownership across contexts, deadlines as domain time (ADR-008), schedulers as driving adapters (7.9)
Your turn (design first)
  1. Extend PAY-8: Open → EvidenceSubmitted → Won | Lost, or Open → Accepted. Decide which disputes are worth fighting (amount, reason code, whether the ticket was scanned at the gate) as a DisputePolicy domain service, and keep "accept" as its default.
  2. Deadlines: dispute.IsOverdue(now) is a pure function. A scheduler emits payments.dispute_response_due.v1 a day before the deadline and auto-accepts at the deadline.
  3. Evidence: Payments owns the process, Ticketing owns the facts (order, ticket scans, emails sent). Design the conversation: Payments asks by event, Ticketing answers with an evidence bundle by event. Payments must never learn what a ticket is.
  4. A won dispute: money comes back. Do the tickets come back? (If the show hasn't happened, maybe.) Does the denylist entry get lifted automatically, or only by staff? Write it as rules first.
  5. Record your decisions as new ADRs, starting at ADR-E18.
