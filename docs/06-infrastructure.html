Why so few dependencies?

Every framework is one more thing between you and the concept you're learning. net/http, log/slog and testing are enough. The only real dependencies are drivers (pgx, franz-go) and the two code tools (sqlc, goose).

Docker Compose (target shape)

services:
  postgres:
    image: postgres:18
    environment: { POSTGRES_USER: stagehand, POSTGRES_PASSWORD: stagehand, POSTGRES_DB: stagehand }
    ports: ["5432:5432"]

    ports: ["9092:9092"]
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:19092,CONTROLLER://:9093,EXTERNAL://:9092
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:19092,EXTERNAL://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT,EXTERNAL:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"   # topics are declared explicitly (kafka-init)
    healthcheck: { test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092"], interval: 5s, retries: 30 }

  kafka-init:                           # one-shot: creates topics, then exits
    image: apache/kafka:4.1.0
    depends_on: { kafka: { condition: service_healthy } }
    entrypoint: ["/bin/sh", "-c", "for t in venue.events show.events ticketing.events ticketing.internal; do
      /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka:19092 --create --if-not-exists --topic $$t --partitions 3; done"]

  kafka-ui:
    image: kafbat/kafka-ui:latest
    ports: ["8081:8080"]
    environment: { KAFKA_CLUSTERS_0_NAME: local, KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: kafka:19092 }

  migrate:                              # one-shot: same image as the app, different subcommand
    build: .
    command: ["migrate", "up"]
    environment: { DATABASE_URL: postgres://stagehand:stagehand@postgres:5432/stagehand?sslmode=disable }
    depends_on: { postgres: { condition: service_healthy } }

  app:
    build: .
    command: ["serve"]
    ports: ["8080:8080"]
    environment:
      DATABASE_URL: postgres://stagehand:stagehand@postgres:5432/stagehand?sslmode=disable
      KAFKA_BROKERS: kafka:19092
      HOLD_TTL: 10m
    depends_on:
      migrate:    { condition: service_completed_successfully }
      kafka-init: { condition: service_completed_successfully }

volumes: { pgdata: {} }

The image is a multi-stage Dockerfile: golang:1.27 builds a static binary (CGO_ENABLED=0), and gcr.io/distroless/static runs it. One binary, stagehand, with two subcommands: serve and migrate.

Postgres: one database, one schema per context

db/migrations/
  00001_create_schemas.sql            -- CREATE SCHEMA venue; CREATE SCHEMA show; CREATE SCHEMA ticketing; …
  00002_venue_tables.sql              -- venue.venues, venue.sections, venue.outbox
  00003_show_tables.sql               -- show.shows, show.venue_layouts (projection), show.outbox
  00004_ticketing_tables.sql          -- ticketing.inventories, ticketing.seats, ticketing.holds, orders, tickets, outbox
  …
Why schemas and not separate databases?

Schemas give each context its own namespace and make ownership visible (ticketing.orders), while running one Postgres. The rule "no cross-schema joins or FKs" keeps contexts separable. A stretch exercise is to give each context its own DB role with privileges only on its schema, so the database enforces the boundary too.

goose migration format

-- +goose Up
CREATE TABLE venue.venues (
    id         UUID PRIMARY KEY,
    name       TEXT        NOT NULL,
    street     TEXT        NOT NULL,
    city       TEXT        NOT NULL,
    country    CHAR(2)     NOT NULL,
    status     TEXT        NOT NULL,
    version    INT         NOT NULL,          -- optimistic concurrency
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL
);

-- +goose Down
DROP TABLE venue.venues;

Migrations are embedded in the binary (//go:embed in package db), so the migrate subcommand, the integration tests and CI all run exactly the same files.

sqlc

# sqlc.yaml
version: "2"
sql:
  - engine: postgresql
    schema: db/migrations                 # sqlc understands goose's Up/Down annotations
    queries: db/queries/venue
    gen:
      go:
        package: sqlcgen
        out: internal/venue/adapters/driven/postgres/sqlcgen
        sql_package: pgx/v5
        emit_pointers_for_null_types: true
        overrides:
          - db_type: uuid
            go_type: github.com/google/uuid.UUID
          - db_type: timestamptz
            go_type: time.Time
  # … one entry per context (show, ticketing): each context gets its OWN generated package
-- db/queries/venue/venues.sql
-- name: UpdateVenue :execrows
UPDATE venue.venues
SET name = $2, status = $3, version = version + 1, updated_at = $4
WHERE id = $1 AND version = $5;          -- 0 rows ⇒ someone else saved first ⇒ ErrConcurrentModification
sqlc types stay in the adapter

Generated structs (sqlcgen.VenueVenue) are persistence models. They never leave adapters/driven/postgres. The repository maps rows ↔ aggregates (via domain.RehydrateVenue). If you catch a sqlcgen import in application, the hexagon has a leak.

Makefile (target shape)

up:               ## start postgres, kafka, kafka-ui, migrate, app
	docker compose up -d --build --wait
down:             ## stop everything (keep data)
	docker compose down
reset:            ## stop everything and wipe volumes
	docker compose down -v
infra:            ## only postgres + kafka (+ init), for running the app from your IDE
	docker compose up -d --wait postgres kafka kafka-init kafka-ui
migrate:          ## apply migrations against $DATABASE_URL
	go run ./cmd/stagehand migrate up
generate:         ## sqlc
	go tool sqlc generate
lint:
	golangci-lint run
test:             ## fast tests
	go test ./...
test-integration:
	go test -tags=integration ./...
test-e2e: up
	go test -tags=e2e -count=1 ./test/e2e/...
run:              ## app on the host against `make infra`
	go run ./cmd/stagehand serve
