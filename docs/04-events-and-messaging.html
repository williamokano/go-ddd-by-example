Events & messaging

How a fact recorded by an aggregate in one context reliably becomes a reaction in another: domain events, integration events, the transactional outbox, Kafka, idempotent consumers and sagas.

Why not publish domain events directly?

If other contexts decode your domain events, your internal model becomes their dependency. Renaming a field or splitting an aggregate would break consumers you don't control. The translation step (domain → integration) is a small Anti-Corruption Layer pointing outward, and it gives you the freedom to refactor inside.

The dual-write problem

A use case must (1) save the aggregate to Postgres and (2) publish an event to Kafka. These are two systems, so there's no shared transaction:

  • Save then publish: the process crashes between the two, the event is lost, and Ticketing never opens the inventory.
  • Publish then save: the save fails, and you've announced something that never happened.

Solution: the transactional outbox

Write the events into an outbox table in the same Postgres transaction as the aggregate. Either both are committed or neither is. A separate process, the relay, reads unpublished outbox rows, publishes them to Kafka, and marks them published.

 use case                    Postgres (one transaction)                 relay (loop)                 Kafka
 ────────                    ──────────────────────────                 ────────────                 ─────
 venue.Activate(now)
 repo.Save(venue) ────────▶  BEGIN
                             UPDATE venue.venues … WHERE version = 4
                             INSERT INTO venue.outbox (id, topic, key, type, payload)
                             COMMIT
                                                     ◀── SELECT … WHERE published_at IS NULL
                                                         ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED
                                                         produce(topic, key, payload) ───────────▶  venue.events
                                                         UPDATE … SET published_at = now()

The result is at-least-once delivery: if the relay crashes after producing but before marking the row, it publishes the row again on restart. So every consumer must tolerate duplicates.

-- one outbox table per context schema, e.g. venue.outbox
CREATE TABLE venue.outbox (
    id           BIGSERIAL PRIMARY KEY,          -- relay order
    event_id     UUID        NOT NULL UNIQUE,    -- dedup key for consumers
    topic        TEXT        NOT NULL,
    msg_key      TEXT        NOT NULL,           -- aggregate id ⇒ per-aggregate ordering in Kafka
    event_type   TEXT        NOT NULL,           -- "venue.activated.v1"
    payload      JSONB       NOT NULL,
    occurred_at  TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ
);
CREATE INDEX ON venue.outbox (id) WHERE published_at IS NULL;
Who writes the outbox? (decision)

The repository's Save writes the outbox rows. It pulls the aggregate's pending events, translates them, and inserts them in the same transaction as the aggregate. One aggregate per transaction (Chapter 2) means Save is the transaction, so this is both simple and correct. The alternative (a Unit of Work port the application service drives) comes up in Part 8, when we need the inbox in the same transaction as a handler.

  • One topic per producing context, keyed by aggregate ID. Kafka only guarantees order within a partition, and the same key always goes to the same partition. So venue.activated is always seen before venue.retired for the same venue. Putting each event type in its own topic would lose that guarantee.
  • Consumer group per consuming context, so Show and Notifications each get every message from ticketing.events, independently.
  • ticketing.internal keeps the saga durable and retryable with the same machinery. It's private: no other context subscribes, and its payloads aren't a public contract.

The envelope

{
  "event_id":       "0192f1c4-…",                 // UUIDv7, unique per event; the dedup key
  "event_type":     "show.published.v1",
  "occurred_at":    "2026-11-02T19:00:00Z",
  "aggregate_id":   "0192f1c2-…",
  "correlation_id": "0192f1aa-…",                 // the request/saga this belongs to (Part 8)
  "causation_id":   "0192f1b9-…",                 // the event_id that caused this one
  "payload":        { … contracts.ShowPublishedV1 … }
}

The envelope fields also go into Kafka headers, so a consumer can route on event_type without decoding the payload.

Found while building it (Parts 8.3 and 9.7)

A trace has to cross the outbox. The span that wrote the event is long gone when the relay publishes it, so its traceparent is stored in the outbox row (column trace_parent), copied into a traceparent Kafka header by the relay (not into the envelope: it's transport metadata, not part of the fact), and picked up by the consumer runner, which starts a child span. Since 9.7 the correlation ID is the trace ID, so a log line and a Jaeger trace find each other.

Consuming: the driving side

A Kafka consumer is a driving adapter, just like an HTTP handler. It decodes a message into a contracts type, translates it into a command in the receiving context's language (this is the ACL), and calls a use case.

ticketing.events ──▶ show/adapters/driving/consumer
                       decode envelope; switch event_type
                       "ticketing.inventory_sold_out.v1" → application.MarkShowSoldOut{ShowID: p.ShowID}
                     ──▶ show/application MarkShowSoldOutHandler.Handle(...)
                     ──▶ show/domain show.MarkSoldOut()   // no-op if already SoldOut (SHW-8)
                     commit Kafka offset only after Handle returns nil

Delivery guarantees and how we cope

RealityOur answer
Duplicates (at-least-once)1) Natural idempotency in the domain: OpenInventory for an existing show is a no-op, and MarkSoldOut on a SoldOut show is a no-op. Unit-tested. 2) An inbox table (consumer, event_id) as a safety net (Part 8).
Reordering across topicsWithin one topic and key (one aggregate), order is preserved, so show.published always arrives before show.cancelled. Across topics there's no order: a ticketing.inventory_sold_out can reach Show after Show has cancelled that show. Handlers check state and treat "too late" facts as no-ops, not errors (SHW-8).
Transient failure (DB down)Retry in place with exponential backoff, capped, for as long as it takes. The offset isn't committed, so the partition waits. Dead-lettering a message only because the database was down would lose it (ADR-015).
Poison message (can't decode, rule violation)The handler says so by wrapping the error in kafka.Permanent. The runner publishes it to <topic>.dlq at once, with the error in a header, logs it, commits, and moves on. Retrying it would never help.
Eventual consistencyAccepted by design: a show becomes SoldOut a few hundred ms after the last ticket is sold. The business is fine with that, and the e2e tests poll with a timeout.
Found in the failure drills (Part 8.5, ADR-015)

The first runner dead-lettered any error after N attempts. Drill 4 (stop Postgres while messages flow) showed the cost: every message consumed during the outage ended up in the DLQ, and its effect was lost. The fix splits the two cases: only an error the handler marks as Permanent is poison; everything else blocks the partition and retries. "Never block a partition forever" became "never block it for a message that can't succeed".

The checkout saga (choreography)

Since Part 9.4 (ADR-014)

The same steps also run orchestrated: a CheckoutProcess per order (started → awaiting_seats → completed | compensated) decides the next step, and a CheckoutOrchestrator runs it. SAGA_STYLE=orchestration (the default) or choreography picks one; the e2e suite passes with both. Since 9.1 (ADR-013) OrderPaid carries the section, because ConfirmHold loads a SectionInventory, not the whole show's.

Paying and confirming seats touches two aggregates (Order and ShowInventory) and an external system. One aggregate per transaction, plus payment providers that can't join a transaction anyway, means a saga.

HTTP POST /orders ─▶ PlaceOrder:      inventory.Get (read-only check: hold valid, owned) → Order.Place → save   [tx1: Order]
                     ChargeOrder:     PaymentGateway.Charge(order.Total)  (external, no tx)
                                      ├─ ok   → order.MarkPaid(paymentRef)  → save → OrderPaid            [tx2: Order]
                                      └─ fail → order.MarkPaymentFailed     → save → OrderPaymentFailed   [tx2: Order]

ticketing.internal: OrderPaid ─▶ ConfirmHold:  inventory.ConfirmHold(holdID, orderID, now)                  [tx3: Inventory]
                                      ├─ ok   → SeatsSold (+ InventorySoldOut if last seats)
                                      └─ hold expired/released → HoldConfirmationFailed   (TKT-8)

ticketing.internal: SeatsSold ─▶ IssueTickets: create N Ticket aggregates; order.MarkFulfilled              [tx4: new Tickets + Order]
ticketing.internal: HoldConfirmationFailed ─▶ RefundOrder: PaymentGateway.Refund → order.MarkRefunded      [tx5: Order]   ← COMPENSATION
Discuss in Part 7
  • Why does PlaceOrder only read the inventory instead of modifying it?
  • tx4 creates several Ticket aggregates and updates the Order. Is that a violation of "one aggregate per transaction"? (Creating fresh aggregates nobody else can see yet causes no contention. Discuss whether that's a good enough reason.)
  • What if Charge succeeds but the process crashes before tx2? (Payment idempotency key = order ID, plus a reconciliation job. Real systems do both.)

Evolving contracts

  1. Additive changes (a new optional field) go into the same version. Consumers ignore unknown fields (Go's encoding/json does by default).
  2. Breaking changes (rename, remove, change meaning) need a new type, show.published.v2. Publish v1 and v2 side by side until every consumer has migrated, then retire v1. Consumers keep recognising v1 after that, to skip it: old records stay in the topic until retention drops them (9.3).
  3. Contracts have golden-file tests (Chapter 5). A diff in the JSON shape fails CI, so a breaking change can't slip through unnoticed.
  4. Found in 9.8: a new fact that must travel through several contexts (the venue's country, for VAT) is an additive field at each hop: venue.activated.v1.country → Show's VenueLayout → show.published.v2.venue_country → Ticketing. Facts published before the change lack it, so the consumer needs a sensible default or a refusal.
