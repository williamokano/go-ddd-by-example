Decision log (ADRs)

Architecture Decision Records: short notes on what we decided, why, and what it costs. These are the decisions the course is built on. When you make a new one during the course (Part 7 includes one), add it here using the template at the bottom.

ADR-001 — Modular monolith with one package tree per bounded context

Status: accepted.

Context: We want real bounded contexts and asynchronous integration, but one developer, one repo, and simple local runs.

Decision: One Go module and one binary. Each context is a top-level tree under internal/ with its own Postgres schema. Contexts talk only through Kafka integration events.

Consequences: (+) one make up, one debugger session, shared CI. (+) Extracting a context into its own service is a deployment change. (−) Discipline is needed so nobody "just imports" another context. The architecture test enforces it (ADR-002).

Alternatives: microservices (too much ops cost for learning); in-process event bus (simpler, but skips the reliability lessons).

ADR-002 — Hexagonal layering with a pure domain; all ports in application

Status: accepted.

Decision: Each context has domain (pure: stdlib + sharedkernel + uuid), application (use cases + all driven port interfaces, repositories included), adapters/driving/*, adapters/driven/* and contracts. The rules are enforced by internal/archtest.

Consequences: (+) Domain tests need zero doubles. (+) The domain can't do I/O by accident. (−) A domain service that needs data from storage gets it passed in by the application service, which is sometimes slightly more code.

Alternatives: repository interfaces in the domain (Evans' original). Equally valid, but it invites context.Context and I/O into the domain.

ADR-003 — "Driving / driven" naming for ports and adapters

Status: accepted.

Decision: Use Cockburn's terms (driving = the outside calls us; driven = we call the outside) in folder names (adapters/driving, adapters/driven) and in conversation.

Consequences: The names describe who initiates, which is what decides who owns the interface. "Inbound/outbound" describe data direction, which is ambiguous for queries.

ADR-004 — Kafka integration via transactional outbox; Save writes the outbox

Status: accepted.

Decision: Repositories persist the aggregate and insert its translated events into <schema>.outbox in one transaction. A relay publishes outbox rows to Kafka (one topic per producing context, keyed by aggregate ID). Consumers are idempotent.

Consequences: (+) No lost or phantom events. (+) Per-aggregate ordering. (−) At-least-once delivery means duplicates, so handlers must be idempotent. (−) Up to ~poll-interval latency.

Alternatives: CDC with Debezium (an extra moving part); publishing after commit (loses events on crash).

ADR-005 — ShowInventory is one aggregate per show

Status: accepted, to be revisited in Part 9.

Context: TKT-5 (never double-sell) and TKT-2 (all-or-nothing multi-seat holds) must hold immediately, so they need a single consistency boundary.

Decision: One aggregate holds every seat state and active hold for a show, with an optimistic version.

Consequences: (+) The invariants are trivially correct in memory and easy to test. (−) Every hold on the same show serialises on one row's version. Under a hot on-sale, many requests get ErrConcurrentModification; the application service retries a few times. (−) Loading a 50k-seat inventory per request is heavy. The Part 7 load test makes this cost visible.

Alternatives: per-section aggregates (holds limited to one section, much less contention); per-seat rows with a DB unique constraint (scales, but moves the invariant into the database).

ADR-006 — sqlc + pgx instead of an ORM

Status: accepted.

Decision: Hand-written SQL in db/queries/<ctx>, generated into a per-context sqlcgen package, used only by that context's driven Postgres adapter.

Consequences: (+) No hidden queries, compile-time-checked SQL, explicit mapping to aggregates (which is good practice for keeping persistence out of the domain). (−) More mapping code, written by hand.

ADR-007 — Fakes over mocks; testcontainers for adapters; build tags per level

Status: accepted.

Decision: Application tests use hand-written in-memory fakes, verified by shared repository contract suites. Adapter tests use real Postgres and Kafka through testcontainers (integration tag). Full-stack tests use the e2e tag. No mocking library.

Consequences: (+) Tests check behaviour and survive refactors. (−) Fakes have to be maintained, which the contract suites keep honest.

ADR-008 — Time and identity are inputs to the domain

Status: accepted.

Decision: Domain methods receive now time.Time and pre-generated IDs as parameters. The application layer gets them from the Clock and IDGenerator driven ports. IDs are UUIDv7.

Consequences: (+) Deterministic tests, no sleeping, and expiry logic (TKT-4) is easy to test. (−) Slightly longer method signatures.

ADR-009 — Shared kernel limited to Money and the domain-event building block

Status: accepted (the extraction happens in Part 7).

Decision: internal/sharedkernel contains only Money, Currency, DomainEvent and the Events recorder. Show first implements Money locally. When Ticketing needs identical semantics, it's promoted.

Consequences: (+) The kernel is justified by real reuse. (−) Every change to it is a cross-context change, so it has to stay tiny.

ADR-010 — Checkout as a choreographed saga with compensation

Status: accepted.

Decision: PlaceOrder → Charge → OrderPaid → ConfirmHold → SeatsSold → IssueTickets, with HoldConfirmationFailed → RefundOrder as compensation. Each step is its own transaction on one aggregate, linked by events on ticketing.internal.

Consequences: (+) Respects aggregate boundaries; each step is retryable. (−) The flow is spread across handlers. The Chapter 4 diagram and the e2e scenarios S1/S3 are its documentation.

Alternatives: an orchestrator (an explicit state machine aggregate Checkout). Worth comparing in Part 9.

ADR-011 — Optimistic concurrency with a version column

Status: accepted.

Decision: Each aggregate root table has a version. UPDATE … WHERE id=$1 AND version=$n affecting 0 rows → application.ErrConcurrentModification. The application layer may retry the whole load-decide-save cycle (bounded, e.g. 3×).

Consequences: (+) No long-held locks, and conflicts are explicit. (−) Hot aggregates see retries (ADR-005).

Template for new ADRs

<h2>ADR-0XX — Title in the imperative or as a statement</h2>
<p><strong>Status:</strong> proposed | accepted | superseded by ADR-0YY.</p>
<p><strong>Context:</strong> the forces at play; what problem; what constraints.</p>
<p><strong>Decision:</strong> what we will do.</p>
<p><strong>Consequences:</strong> (+) gains, (−) costs, what becomes easier/harder.</p>
<p><strong>Alternatives:</strong> what else we considered and why not.</p>
