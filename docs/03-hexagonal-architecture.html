Hexagonal architecture (ports & adapters)

How the code is organised, which way dependencies point, what a port is, and exactly which folder each kind of thing goes in.

The idea in one sentence

Put the business logic in the centre, have it declare what it needs as interfaces (ports), and plug the outside world (HTTP, Postgres, Kafka, clocks, payment providers) in through adapters that implement or call those interfaces. Alistair Cockburn described it in 2005 to make "the application equally driven by users, programs, automated tests or batch scripts, and developed and tested in isolation from its eventual run-time devices and databases."

Hexagonal, Onion and Clean Architecture are the same core idea with different diagrams. They all follow the dependency rule: source-code dependencies point inward, toward the domain. We use hexagonal vocabulary because it names the two sides of the application explicitly.

Vocabulary: picking the names

A short version, with the "who calls first?" test and a car analogy, is in Key terms. Here is the full mapping.

The same two ideas have several names in circulation. We use "driving" and "driven", Cockburn's own terms and the most widely recognised in the hexagonal literature. The others are equivalent:

Why "driving/driven" over "inbound/outbound"?

"Inbound/outbound" suggests data direction, and that's misleading. A query port is driving but data flows out. A repository Get is driven but data flows in. "Driving/driven" is about who initiates, and that's what decides which side owns the interface.

Rule for creating folders

We never create empty folders "for later". A folder appears in the lesson where its first file (usually a test) is written. The layout above is where we end up, not a scaffold to generate on day one.

Driving ports in Go: an honest note

Hexagonal texts draw driving ports as interfaces such as RegisterVenueUseCase. Go's idiom is "accept interfaces, return structs; define interfaces where they are consumed". We reconcile the two like this:

  • The driving port is the use case's public contract: the command struct, the result type, the errors, and the Handle method. The application layer owns it and exports it as a concrete type, application.RegisterVenueHandler.
  • The HTTP adapter declares a one-method interface for what it consumes (type registerVenue interface{ Handle(context.Context, application.RegisterVenue) (domain.VenueID, error) }) so its own tests can pass a stub.
  • Driven ports are always interfaces declared in application. That's what makes the core swappable and testable.
// internal/venue/application/add_section.go
type AddSection struct {          // the command: primitives only, comes from any driving adapter
	VenueID  string
	Code     string
	Kind     string               // "seated" | "ga"
	Rows     []RowSpec
	Capacity int
}

type AddSectionHandler struct {
	venues VenueRepository        // driven port
	clock  Clock                  // driven port: time is an input (ADR-008)
}

func NewAddSectionHandler(venues VenueRepository, clock Clock) *AddSectionHandler { ... }

func (h *AddSectionHandler) Handle(ctx context.Context, cmd AddSection) error {
	id, err := domain.ParseVenueID(cmd.VenueID)       // 1. parse into domain types
	...
	venue, err := h.venues.Get(ctx, id)               // 2. load
	...
	if err := venue.AddSection(section, h.clock.Now()); err != nil { // 3. ONE behaviour call; rules live in the domain
		return err
	}
	return h.venues.Save(ctx, venue)                  // 4. save (+ outbox, atomically)
}

Composition root

cmd/stagehand/main.go is the only place that knows every concrete type. It reads config, opens the pool, builds the adapters, injects them into use-case handlers through constructors, mounts the routes, starts the consumers, the outbox relay and the scheduler, and handles graceful shutdown. No DI container and no globals: plain constructor injection that you can read top to bottom.

Rules between bounded contexts

  1. A context never imports another context's domain, application or adapters.
  2. A context may import another context's contracts package, and only to decode its integration events.
  3. Each context owns a Postgres schema (venue, show, ticketing). No cross-schema joins and no foreign keys across schemas.
  4. Contexts communicate asynchronously via Kafka. There are no in-process calls across contexts, even though it's one binary. That keeps a future split into services cheap.

Commands vs queries (CQRS-lite)

Writes go through aggregates, because that's where the rules are. Reads don't need aggregates: loading a full ShowInventory to show a list of shows wastes work and couples screens to the model. For queries, the application layer declares a query port that returns flat view DTOs, and the Postgres adapter implements it with straight SQL through sqlc. Same database, separate paths. We don't use separate read databases or event sourcing.
