Integration events: outbox, relay, Kafka

The second piece of infrastructure. Venue's domain events become public integration events, are written to the outbox in the same transaction as the aggregate, and are relayed to Kafka. We also build the consumer machinery that Show and Ticketing will use.

Read Chapter 4 before starting this part.

5.2 The Published Language: venue/contracts

Goal
Define the public, versioned shape of venue.activated.v1 and venue.retired.v1.
Concepts
Domain vs integration events, Open Host Service + Published Language
Creates
internal/venue/contracts/events.go (Topic, type constants, payload structs), events_test.go, testdata/*.golden.json
TDD script
  1. Golden test: a known VenueActivatedV1 marshals to exactly testdata/venue.activated.v1.golden.json (with an -update flag to regenerate).
  2. The same for VenueRetiredV1.
  3. Unmarshalling a payload that has an extra unknown field still works (forward compatibility).
Rule

contracts imports only stdlib. It uses no domain types, because consumers must be able to depend on it without depending on your model.

5.3 Writing the outbox atomically

Goal
Save persists the aggregate and its translated events in one transaction (ADR-004).
Creates
db/migrations/0000N_venue_outbox.sql; internal/platform/outbox/{message,writer}.go; internal/venue/adapters/driven/postgres/events.go (domain → contracts translation)

Not every domain event becomes an integration event. VenueRegistered and SectionAdded are internal facts nobody outside needs. Only VenueActivated and VenueRetired are translated. The translator decides that.

TDD script
  1. Unit: the translator maps VenueActivated → one outbox.Message (topic venue.events, key = venue ID, type venue.activated.v1, payload JSON) and maps SectionAdded → nothing.
  2. Integration: activating and saving a venue leaves exactly one unpublished outbox row with the expected type and key.
  3. Integration: a save that fails with ErrConcurrentModification leaves no outbox row. This is the whole point of atomicity.

5.4 The relay

Goal
A loop that moves outbox rows to Kafka with at-least-once semantics.
Creates
internal/platform/outbox/relay.go (depends on a Publisher interface), internal/platform/kafka/producer.go (franz-go implementation)

Notice the pattern repeating inside platform: the relay declares a Publisher port, and Kafka is just one adapter. The relay's logic can be unit-tested with a fake publisher.

TDD script
  1. Unit (Postgres + fake publisher): pending rows are published in id order and marked published.
  2. A publisher error leaves the rows unpublished and they're retried next tick.
  3. Two relays running at once (FOR UPDATE SKIP LOCKED) never publish the same row in the same tick.
  4. Integration (Postgres + Kafka containers): an outbox row ends up on the topic with the envelope headers and the aggregate ID as key.
Discuss

The relay crashes after Kafka acknowledged the message but before the UPDATE … published_at. What happens on restart? Who has to cope with that?

5.5 The consumer runner

Goal
Reusable consumer-group plumbing, so context consumers only write "event type → command".
Creates
internal/platform/kafka/consumer.go: Run(ctx, group, topics, handler func(ctx, Envelope) error)
TDD script (integration)
  1. A produced message reaches the handler with a decoded envelope.
  2. The offset is committed only after the handler succeeds. After a restart, a message whose handler failed is delivered again.
  3. After N failures the message goes to <topic>.dlq with an error header, and consumption continues.
  4. Context cancellation stops the runner cleanly.
