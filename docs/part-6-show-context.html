The Show context

The second context, built faster because you know the moves. The new ideas are a domain service, an anti-corruption layer that consumes another context's events into a local projection, a richer state machine, and policies reacting to other contexts. From here on we work outside-in.

Change of rhythm: double-loop TDD

Each feature now starts with a failing acceptance test (the outer loop) that describes it from the outside. It stays red while you go inside-out with unit tests (the inner loops) until it turns green. You'll get less step-by-step guidance from here: I'll set the goal and the tests, you lead, and I review.

6.2 Value objects: ShowID, Schedule, Money, PriceList

Rules
SHW-2, SHW-4
Creates
internal/show/domain/{show_id,schedule,money,price_list}.go + tests
TDD script
  1. NewSchedule(doors, start, end): table of valid and invalid orderings, durations over 12h, and the zero time.
  2. schedule.Overlaps(other): touching edges don't overlap; containment does. Use a table.
  3. Money in minor units (int64 cents) plus a Currency. Add fails on a currency mismatch, negative amounts are rejected, and String() gives "EUR 15.00".
  4. PriceList.CoversExactly(sectionCodes): missing, extra and exact cases. Mixed currencies → error.
Pitfall

Never float64 for money: 0.1 + 0.2 != 0.3. Use integer minor units.

Discuss

We just wrote Money inside show/domain. Ticketing will need it too. Why not put it in a shared package right away? (ADR-009, the rule of three, and the cost of a premature shared kernel.)

6.3 The Show aggregate and its state machine

Rules
SHW-1, SHW-5, SHW-6, SHW-8
Creates
show.go, events.go, errors.go + tests

Methods: DraftShow(id, venueID, promoterID, title, schedule, now), Price(list, venueSections, now), Reschedule(schedule, now), Publish(now), Cancel(reason, now), MarkSoldOut(now).

TDD script
  1. A drafted show records ShowDrafted and is Draft.
  2. Drafting with a start in the past (relative to now) → error.
  3. Publishing without a price list → ErrShowNotPriced. With a complete list → Published + ShowPublished.
  4. Transition table: for every (state × command) pair, the expected result is "ok → new state" or a specific error. One table-driven test covers the whole state diagram from Chapter 1.
  5. MarkSoldOut on a SoldOut show is a no-op and records no event (SHW-8, idempotency in the domain).

6.4 Domain service: SchedulingPolicy

Goal
A rule that no single aggregate can enforce (SHW-3).
Concepts
Domain service
Creates
scheduling_policy.go + tests
TDD script
  1. No other shows → ok.
  2. An overlapping, non-cancelled show at the same venue → ErrScheduleConflict that names the conflicting show.
  3. An overlapping cancelled show → ok.
  4. The show being rescheduled is excluded from the comparison with itself.
Discuss
  • The policy takes []Show (or []Schedule). Who loads them, and with what query? (The application layer, through a repository finder FindActiveAt(venueID, window).)
  • Two promoters draft overlapping shows at the same instant, and both checks pass. Is that a real risk? How would you close it? (A unique/exclusion constraint in Postgres as a backstop: EXCLUDE USING gist. The domain rule stays the primary statement of the rule.)

6.5 Anti-corruption layer: the local VenueLayout projection

Goal
Show learns about venues only through events, translated into its own model.
Concepts
ACL, projections, idempotent consumers, policies
Creates
show/application/venue_events.go (OnVenueActivated, OnVenueRetired handlers), a VenueLayouts port, show/adapters/driving/consumer/venue_consumer.go, the Postgres show.venue_layouts table
venue.events ─▶ consumer (driving adapter)          ─▶ application                                  ─▶ domain
                decode contracts.VenueActivatedV1      OnVenueActivated: upsert VenueLayout
                translate → OnVenueActivated{…}         OnVenueRetired:  mark retired; for each future show:
                                                                         show.Cancel("venue_retired")  (SHW-7)
TDD script
  1. Application: OnVenueActivated stores a layout that DraftShow can then use.
  2. Receiving the same event twice leaves the same state (an upsert).
  3. OnVenueRetired cancels only future, non-terminal shows at that venue, one aggregate save per show.
  4. Consumer: a venue.activated.v1 envelope is translated into the right command, and an unknown event type is ignored and logged (not an error).
Why a local copy instead of asking Venue?

Show can now draft shows while Venue is down, and Venue's model can change without breaking Show, because only the contract matters. The cost is that the data is eventually consistent, which is why the e2e test uses eventually.

6.6 Use cases, adapters, contracts, and the outer loop goes green

Creates
DraftShow, PriceShow, PublishShow, CancelShow, MarkShowSoldOut handlers; Postgres repo (with a contract suite); HTTP adapter; show/contracts (show.published.v1, show.cancelled.v1) with golden tests; outbox translation; wiring in main
TDD script (highlights)
  1. DraftShow: the venue isn't in the projection → ErrVenueUnknown; venue retired → ErrVenueNotActive; overlap → ErrScheduleConflict.
  2. Authorisation: only the promoter who drafted the show may price, publish or cancel it. This check lives in the application layer. Discuss why.
  3. HTTP: every request that acts for a promoter carries promoterId in its JSON body (there's no login; see chapter 1). A missing or malformed id → 422.
  4. PublishShow writes a show.published.v1 carrying the layout snapshot and prices (from the projection plus the price list).
  5. The 6.1 acceptance test is green.
Retrospective
  • Which parts of Venue did you copy almost verbatim? Which of them are worth extracting into platform, and which are domain code that only looks similar?
  • Is the authorisation rule "only the promoter may cancel" a domain rule or an application rule? Argue both sides.
