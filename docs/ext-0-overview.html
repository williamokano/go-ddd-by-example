Extension track · Optional

Taking Stagehand toward production

You can finish the main course (Parts 0–9) without ever opening these pages. This track takes the finished system and adds what a real platform needs, in small steps, without rewriting what you already built. Every lesson doubles as a test of the architecture: if DDD and hexagonal did their job, most of this is new domain code in the right place, new adapters, new decorators and a couple of new contexts, not surgery.

How this track relates to the course
  • Additive only. No existing chapter, rule or ADR is edited; the only changes to existing files are the sidebar entry, a pointer on the welcome page, and two small stylesheet fixes for narrow screens. Where this track changes the meaning of something (for example "Payments: buy it, fake adapter"), it says so and records an extension ADR.
  • Ignorable. Nothing in Parts 0–9 depends on it. Skip it, do it later, or do only the extensions you care about, as long as you respect the prerequisites below.
  • Same rules. Failing test first, simplest code, refactor. The dependency rule and the architecture test still apply, and several lessons extend that test.
  • Same format. Lessons use the same "Goal / Rules / Your turn / TDD script / Discuss" shape, with ids like E5.3 and progress ticks in the sidebar. Track your progress in tasks/extension.md, separate from the course checklist.

The six extensions

E1 · Pricing domain

Dynamic prices, discounts, fees and taxes. Almost pure domain modelling: value objects, specifications, domain services, and a price lock inside the inventory aggregate.

E2 · Identity & access cross-cutting

Who is calling, and what may they do? Local user/password and pluggable SSO providers side by side. RBAC around the use cases, ownership rules from the domain.

E3 · Observability cross-cutting

Prometheus metrics and Grafana dashboards in an optional Compose profile. Instrument through decorators and adapters, never the domain.

E4 · Audit trail cross-cutting

Now that we know the caller, record who did what: command-level attempts plus actor-enriched events, in an append-only log.

E5 · Payments new context

A real Stripe sandbox integration that never leaks Stripe into our language. Authorize/capture, refunds as a feature added to an existing domain, chargebacks from the outside world, and a denylist so a charged-back customer can't buy again.

E6 · Fraud screening new context

A third-party risk vendor we call synchronously before payment and feed asynchronously afterwards. We only ever use a fake; the architecture is the lesson.

New ubiquitous language

These terms extend the glossary in chapter 0 (that page isn't edited). Keep this table nearby.

TermMeaning in Stagehand
List price / selling priceThe promoter's price per section (Show) / what a customer pays per seat after demand adjustment, decided when the seat is held (Ticketing).
Price lockThe selling price quoted for a hold stays fixed for that hold.
Price breakdownThe itemised, all-in price of an order: selling prices, discounts, fees, taxes, total.
Inclusive / exclusive taxTax already contained in the price (EU VAT) / added on top (US sales tax).
Basis point (bp)One hundredth of a percent. Rates are stored as integer basis points.
PrincipalThe authenticated actor of a request: a user, or a system (scheduler, webhook). Carried in context.Context.
Role / permissionA role is a named bundle of permissions (venue:register, order:refund). Code checks permissions, never role names.
Identity provider (source)Anything that can vouch for who someone is: our own password store, or an external SSO (OIDC).
Authorization (payment)The issuer reserves funds on the card. No money has moved yet.
CaptureCollect previously authorized funds.
VoidRelease an authorization that was never captured. Cheaper and faster than a refund.
RefundReturn captured money to the customer, fully or partly.
Dispute (chargeback)The cardholder's bank reverses a captured payment and asks us to prove it was legitimate, within a deadline. For now Stagehand accepts every dispute (E5.10).
Denylist / blocked identifierA customer account, email or card fingerprint that may no longer buy. Added automatically on a chargeback, lifted only by staff, never deleted.
ScreeningAsking a fraud vendor to assess a prospective transaction before we try to take money.
Risk decisionOur verdict (Allow / Review / Block), derived from vendor signals plus our own policy.
Issuer fraud reportThe cardholder's bank reporting a transaction as fraud (Visa TC40, Mastercard SAFE). A risk signal only: no dispute, no deadline.
Pre-dispute alertA warning (Ethoca, Verifi) that a transaction will become a dispute unless it's refunded within a short window.
Outcome feedbackTelling the fraud vendor what really happened to a transaction (captured, declined, refunded, charged back) so its model improves.

New rule ids

Numbering continues the main course's scheme so review comments stay unambiguous. PRC-*, AUTH-*, AUD-*, PAY-*, DNY-* and FRD-* are new families. The existing contexts get VEN-8 (E2) and TKT-13…TKT-19 (E5 and E6). Each rule is defined in the lesson that introduces it.

Ground rules for every lesson in this track

  1. Never name the vendor in the domain. No stripe, PaymentIntent or vendor score type in domain or application. The architecture test grows a rule for this.
  2. Every external system gets a fake first, with scriptable behaviour (decline, time out, duplicate, reorder). The real adapter must pass the same contract tests as the fake.
  3. Every new capability can be switched off or starts off: demand pricing, metrics, fraud screening and each identity source are configured, with a safe, tested default.
  4. Secrets and personal data stay out of logs, events and audit rows. Card numbers never enter Stagehand at all; the browser sends them straight to the provider.
  5. Additive contracts only. New optional fields or new events. If you must break a contract, use lesson 9.3's playbook.
Honest caveat

"Production-ready" is a direction, not a destination. This track covers the seams where pricing rules, identity, telemetry, audit and external providers plug in. It doesn't cover hosting, secrets management, PCI scoping paperwork, rate limiting at the edge, or GDPR processes. Those come up in "Discuss" prompts so you know what's still on the list.
