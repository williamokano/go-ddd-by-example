8.2 Notifications: when a transaction script is the right answer

Goal
Show that not every context deserves aggregates.
Creates
internal/notifications/: handlers for tickets_issued and order_refunded, an EmailSender port, a logsender adapter, a consumer
TDD script
  1. The handler formats the expected email from a TicketsIssuedV1 (golden text) and sends it to the contact email the event carries. Notifications never looks the customer up anywhere.
  2. A duplicate event doesn't send twice. This needs the inbox from 8.4: write the test now, see it fail, and come back.
Discuss

No domain package, no aggregates, no repository. Is that "bad DDD"? (No. Strategic DDD tells you where not to invest. Generic subdomain, simplest thing that works.)

8.3 Correlation and causation IDs

Goal
Follow one purchase across HTTP, the outbox, Kafka and three contexts in the logs.
TDD script
  1. The HTTP middleware puts a correlation ID in the context (from the X-Correlation-ID header, or a new one).
  2. The outbox writer copies it into the envelope. The consumer runner puts it back into the context, with causation_id set to the consumed event's ID.
  3. A slog.Handler wrapper adds both IDs to every log line.
  4. e2e: after S1, every log line and outbox row for that purchase share one correlation ID.
Discuss

The correlation ID travels in context.Context, and the domain doesn't take a context. How does the ID reach the outbox without touching the domain? (The repository adapter reads it from ctx in Save.)

8.4 Inbox and a transaction manager

Goal
Effectively-once processing for handlers that aren't naturally idempotent (sending emails, calling the payment provider).
Creates
A <schema>.inbox (consumer, event_id) table; a TxManager port (WithinTx(ctx, fn)) with a context-carried pgx.Tx; repositories join an ambient transaction when there is one
TDD script
  1. The inbox insert and the handler's writes commit together, or roll back together.
  2. A second delivery of the same event_id is skipped.
  3. The 8.2 duplicate-email test now passes.
Discuss

We refactored "Save is the transaction" (ADR-004) into "the use case may open a transaction". Write ADR-012 recording this, and explain why we didn't start there.

8.5 Failure drills

Your turn: break it on purpose
  1. Stop Kafka in the middle of S1. Purchases still complete their HTTP part and the outbox grows. Restart Kafka, and everything converges.
  2. Kill the app while the relay is publishing. On restart, duplicates are delivered and absorbed by idempotency.
  3. Publish a malformed message to show.events by hand. It ends up in the DLQ, and consumption continues.
  4. Stop Postgres: HTTP returns 500s and consumers back off without losing messages.
Discuss

For each drill, which pattern saved you (outbox, idempotency, offsets committed after handling, DLQ)?
