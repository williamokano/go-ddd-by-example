Observability: metrics, Prometheus and Grafana

Part 8 gave you correlation IDs and 9.7 sketched tracing. Now you'll answer "is it healthy, and is the business working?" with numbers: metrics scraped by Prometheus, drawn in Grafana, and optional. The architectural question is the same as in E2: how do we instrument everything without the domain ever knowing a metrics library exists?

Where instrumentation belongs

What you want to measureWhere to hook inWhy not the domain
HTTP rate, errors, duration (RED)HTTP middleware (driving adapter)It's about the transport.
Use-case rate, errors, durationA decorator, assembled in the composition root (the same trick as E2.6)Same shape for every use case.
Business facts: seats held, orders paid, refundsA consumer of each context's own events, plus use-case outcomesEvents already say what happened; the model needn't change.
Infrastructure health: outbox lag, consumer lag, DB pool, Kafka errorsInside the relevant adapter or a small collectorOnly adapters know about these.
Design decision (ADR-E08)

The domain and application packages never import a metrics library. Decorators and adapters take a small interface from internal/platform/telemetry (a Registry that creates counters and histograms), with a Prometheus implementation and a no-op implementation. The no-op is what runs when metrics are switched off: a null object, so no if enabled checks are scattered around the code.

E3.1 A metrics endpoint and the RED trio for HTTP

Goal
Expose /metrics and record request rate, errors and latency for every route.
Creates
internal/platform/telemetry/{registry,prom,noop}.go, platform/httpx/metrics.go
New dependency
github.com/prometheus/client_golang (the only place it's imported is telemetry/prom)
TDD script
  1. A request through the middleware increments http_requests_total{route,method,code} exactly once; a failing handler is counted with its status code.
  2. Label by route pattern (/venues/{id}), never by raw path. The mux records the matched pattern in r.Pattern (Go 1.23+), so the middleware can read it after the inner handler returns. Test that two different venue ids produce one series, not two, and that unmatched paths share a single route="unmatched".
  3. Duration goes into a histogram; assert a handler that sleeps lands in the right bucket (inject a fake clock or use a small sleep with generous bounds).
  4. With METRICS_ENABLED=false (a new row in chapter 6's config table, parsed in platform/config) the registry is the no-op one, /metrics returns 404, and the handlers behave identically.
Pitfall: cardinality

Every distinct label value is a new time series in memory forever. User IDs, order IDs, raw URLs, error messages and email addresses must never be label values. Rule of thumb: a label's possible values should be a short, fixed list you could write down.

E3.2 A use-case decorator for rate, errors and duration

Goal
Measure every command and query with one decorator, and leave every use-case file alone.
Your turn
  1. Write Observe[C,R](name, reg, next) in platform/telemetry, with the same shape as E2's Require (a struct with a Handle method, so the HTTP adapters accept it). It records usecase_duration_seconds{usecase,outcome} where outcome is one of a small enum: ok, domain_error, forbidden, conflict, internal.
  2. Classify errors with errors.Is against your domain/application sentinel errors, not by string-matching messages.
  3. If you did E2, decide and test the decoration order: should Observe wrap Require or sit inside it? What does each choice show you about forbidden calls?
Discuss

An optimistic-concurrency conflict (ADR-011) is an expected outcome under contention, not a failure. Should it count as an error in the dashboard's error rate? What does your answer say about what "error" means for a business?

E3.3 Business metrics from events and outcomes

Goal
Count business outcomes (holds, sales, sell-outs, refunds, emails) without touching an aggregate.
Creates
A small metrics consumer per context that subscribes to that context's own topics; business counters fed from use-case outcomes in the composition root
Which events may a metrics consumer read?

Holds and payments are visible only inside Ticketing: OrderPaid and SeatsSold travel on the private ticketing.internal topic, and there's no "seats held" integration event at all. A Ticketing-owned metrics consumer may read Ticketing's private topic; a generic consumer that reads everyone's private topics would be a boundary leak. For holds, count successful HoldSeats calls in the use-case decorator from E3.2, using the number of seats in the command.

TDD script
  1. A successful HoldSeats with 3 seats increments stagehand_seats_held_total by 3; a rejected one doesn't.
  2. Feeding ticketing.tickets_issued.v1 to the metrics handler increments stagehand_tickets_sold_total by the number of tickets. A duplicate delivery (at-least-once!) over-counts unless you use the inbox from 8.4. Decide whether a few percent of drift is acceptable for this metric, and say why.
  3. stagehand_orders_total{outcome="paid"|"failed"|"refunded"} from Ticketing's own events (OrderPaid on ticketing.internal, ticketing.order_refunded.v1), and failed payments from the Checkout outcome.
  4. stagehand_shows_sold_out_total from ticketing.inventory_sold_out.v1; stagehand_emails_total{kind} inside Notifications.
  5. A gauge of currently held seats can't be rebuilt by counting events after a restart. Compute it from a periodic read query instead (the GET /shows/{id}/seats query from 7.5 is a hint).
Discuss

Which of these metrics are for engineers (is it broken?) and which for the business (is it working)? Who should be able to change the second kind without a deploy?

E3.4 Infrastructure metrics: lag, pools and the outbox

Goal
Make the asynchronous plumbing visible: the first place a messaging system hurts you.
Your turn
  1. Outbox lag: the age of the oldest unpublished row per schema, as a gauge sampled by a collector that runs a cheap query at scrape time (or every few seconds). This is the single most useful metric in the whole system.
  2. Relay and consumer: messages published, publish failures, handler errors by consumer group, and consumer lag if the client exposes it.
  3. Database: expose the pgx pool's stats (acquired, idle, wait count and duration) from the Postgres adapter, not from application code.
  4. Go runtime and process collectors come free from the client library; register them once.
TDD script
  1. With the testcontainers Postgres: insert an old outbox row → the lag gauge reports roughly its age; publish it → the lag drops to 0.
  2. The collector must not hold the scrape hostage: a slow query times out and reports a "scrape error" metric rather than blocking /metrics.

E3.5 Prometheus and Grafana as an optional Compose profile

Goal
make up still gives you the original stack; make up-obs adds Prometheus and Grafana with a ready-made dashboard.
Creates
deploy/prometheus/prometheus.yml, deploy/grafana/provisioning/{datasources,dashboards}/*, deploy/grafana/dashboards/stagehand.json, Compose services with profiles: ["observability"], Make targets
Your turn
  1. Add the two services to docker-compose.yml under a profile. Services without a profile are unaffected, so the default stack doesn't change. Add make up-obs (docker compose --profile observability up -d --build --wait). Make make down pass --profile observability as well: Compose only acts on the profiles you name, so a plain down can leave Prometheus and Grafana running.
  2. Configure the scrape job against the app's /metrics (app:8080 inside Compose; host.docker.internal:8080 when you use make run on the host). Provision the Grafana datasource and dashboard from files, so a fresh make up-obs shows the dashboard without clicking anything.
  3. Build one dashboard with four rows: HTTP RED, use cases (p50/p95/p99 from the histogram with histogram_quantile), business (orders by outcome, seats held vs sold), plumbing (outbox lag, consumer errors, DB pool wait).
  4. Prove "turn it off" both ways: make up never starts the observability containers, and the e2e suite passes with METRICS_ENABLED=false set on the app service.
Pitfall

Dashboard JSON exported from the UI is noisy and full of generated IDs. Keep it in the repo, review it like code, and note the Grafana version in the file. Treat "I edited it in the UI" as an unsaved change.
