Extension track · Reference

Extension decision log (ADR-E*)

Decisions made for the optional extension track. They extend the main decision log; none of them edits or supersedes an existing ADR. Where one narrows or reinterprets an earlier decision, it says so.

ADR-E01 — The extension track is additive and ignorable

Status: accepted.

Decision: Extension pages (ext-*.html) are separate from Parts 0–9, with their own progress file (tasks/extension.md). Existing chapters, rules and ADRs are not edited, with one exception: a genuine gap in the main course (the order had no contact email for Notifications) was fixed there, in TKT-6, 7.7, 7.8 and 8.2. The main course otherwise carries only a sidebar group and a pointer on the welcome page.

Consequences: (+) The core course stays focused. (+) Extensions demonstrate that the architecture tolerates change. (−) Some statements in earlier chapters are knowingly outdated for a learner who does the extensions; this log and the overview are where that's said.

ADR-E02 — Pricing is a module of Ticketing's domain, not its own context

Status: accepted.

Context: Demand pricing, discounts, fees and taxes all have to be consistent with a specific hold and order, and only Ticketing owns those.

Decision: Pricing lives in internal/ticketing/domain/pricing: value objects (Rate, PriceBreakdown, DemandRules, Promotion, FeeSchedule, TaxRule), specifications and pure domain services (DemandPolicy, DiscountPolicy, TaxPolicy, OrderPricing). Rule data comes in through read-only ports. Show keeps owning the list price (SHW-4).

Consequences: (+) Pricing is tested without I/O, and the package boundary makes a later extraction cheap. (−) Ticketing's domain grows; watch its size. (−) The venue's country has to reach Ticketing through the snapshot, which is an additive contract change in Venue and Show. Alternatives: a Pricing context of its own (premature: there's no separate team or lifecycle yet); pricing in the application layer (untestable rules scattered across use cases).

ADR-E03 — Integer money, basis-point rates, half-up rounding, tax per line

Status: accepted (revisit if a jurisdiction needs finer rates).

Decision: Amounts stay integer minor units. Rates are integer basis points. Rounding is half up (away from zero) and happens only at named steps: each demand-adjusted price, each discount share, each fee, each line's tax. Amounts split across lines use largest-remainder allocation, so the parts always sum to the whole.

Consequences: (+) Totals are reproducible to the cent, and per-ticket refunds are exact. (+) Receipts match what customers expect. (−) Rates such as 8.875% don't fit in whole basis points. (−) Per-line tax can differ by a cent from tax on the order total, so it's documented rather than discovered. Alternatives: decimals via a library (fine, but hides the lesson); banker's rounding (less bias, less intuitive on a receipt).

ADR-E04 — The selling price is decided inside ShowInventory.Hold and locked for the hold

Status: accepted. Extends: ADR-005, TKT-6.

Decision: The inventory stores DemandRules (off by default). Hold computes occupancy before the hold, asks the pure DemandPolicy for each section's unit price, and stores it on the hold. Orders take their prices from the hold. Discounts, fees and taxes are applied at order placement.

Consequences: (+) The price and the occupancy it's based on are consistent, because both sit in one aggregate. (+) Existing tests pass unchanged with the default rules. (+) A customer never sees the price change mid-checkout. (−) Hold rows carry a price column. (−) A preview quote can differ from the held price, so it is labelled non-binding.

ADR-E05 — Principal lives in platform/actor; the domain never sees it

Status: accepted.

Decision: The authenticated actor is a plain value carried in context.Context. application may read it; domain may not import it. When the domain needs "who", the use case passes a plain id.

Consequences: (+) Consistent with ADR-008 (time and identity are inputs). (+) Domain tests need no auth fixtures. (−) A context value is implicit, so a lint/architecture test must keep it confined to the application and adapter layers.

ADR-E06 — Authentication is a strategy over identity providers; local password first

Status: accepted.

Context: We want our own small identity module, with room for several SSO sources side by side, and no extra service to run.

Decision: An IdentityProvider port reduces every source to a VerifiedIdentity. A registry maps provider names to adapters (password, oidc:*). Users link to external identities by (issuer, subject), never by email alone. We issue our own signed tokens.

Consequences: (+) New SSO = new config or adapter. (+) No Keycloak/Dex service. (−) We own password storage, token signing and revocation, which are security-critical; the checklist in E2.9 exists for that. Alternatives: an external IdP as the only source (simplest for production, hides the lesson); Keycloak in Compose (extra service, rejected for now).

ADR-E07 — Authorization: RBAC as a decorator; ownership in the domain

Status: accepted.

Decision: Roles are bundles of permissions; code checks permissions only. Coarse checks are a decorator assembled in the composition root. Rules that depend on business data (venue ownership, VEN-8) are enforced by the aggregate or the use case.

Consequences: (+) Existing use-case bodies are untouched, apart from one ownership guard each in the three venue use cases (E2.7). (+) HTTP adapters take customer and promoter ids from the principal, closing an impersonation hole. (−) A forgotten decoration leaves a route open, so an architecture test requires every route to be wrapped or explicitly public. (−) The e2e suite needs a login helper.

ADR-E08 — Observability by decoration; metrics are optional behind a null object

Status: accepted.

Decision: Domain and application never import a metrics library. HTTP middleware, a use-case decorator, event consumers and adapters take a small telemetry.Registry. A no-op implementation runs when metrics are disabled. Prometheus and Grafana run under a Compose profile.

Consequences: (+) The default stack is unchanged. (+) No if enabled scattered through code. (−) Labels must be curated to avoid cardinality explosions; that's reviewed, not enforced by the compiler.

ADR-E09 — Audit from two sources, through each context's own outbox, stored append-only

Status: accepted.

Decision: A command-level decorator records every attempt (including denied and failed ones) as an audit.command_attempted.v1 record written to the acting context's own outbox, in the same transaction as the change when it succeeds (8.4's TxManager). The outbox envelope also carries the actor, so integration events can be attributed. An audit context consumes both into an append-only table protected by a trigger (and by privileges if 9.6 is done).

Consequences: (+) No context writes into another's schema. (+) A successful change and its audit record commit together. (+) Domain event payloads are unchanged. (−) The trail is eventually consistent with the change (relay latency). (−) Changes that are neither decorated commands nor integration events are invisible; the "what to audit" list in E4.1 is how you find them.

ADR-E10 — Payments becomes its own bounded context, with an Open Host Service for commands

Status: accepted. Relation to earlier decisions: refines the chapter-1 classification of Payments ("generic: buy it") and narrows ADR-001's "Kafka only" for synchronous commands; ADR-010's saga still applies.

Context: Real payments need states, idempotency, webhooks, refunds and disputes: too much to be a two-method port. Authorizing a payment is a request/response conversation.

Decision: A payments context owns the model. Other contexts call it synchronously only through payments/contracts (a versioned Client interface and DTOs, in-process for now). Every outcome leaves as an integration event through the outbox.

Consequences: (+) Ticketing keeps its own port and ACL. (+) Extracting Payments later means swapping the Client implementation. (−) A sanctioned synchronous path exists between contexts, so the architecture test lists exactly which contracts packages may be imported.

ADR-E11 — Provider vocabulary stays inside the adapter

Status: accepted.

Decision: Only adapters/*/stripe imports the SDK or uses its words. The port speaks our types: sealed result sets, a small decline taxonomy, normalized ProviderNotifications, and an opaque ProviderRef. Raw payloads are kept only in the inbox for diagnostics.

Consequences: (+) A second provider is one adapter. (+) The fake and the real adapter share one contract suite. (−) Mapping tables to maintain; unknown values must fail loudly or map to Other, never be guessed.

ADR-E12 — Authorize, then confirm seats, then capture

Status: accepted. Extends: ADR-010 (TKT-8 compensation).

Decision: Checkout authorizes first, confirms seats while funds are reserved, then captures. Failed confirmation cancels the authorization (Payments calls it a void) instead of refunding a capture.

Consequences: (+) No money moves for the common failure; no refund fees. (+) Smaller blast radius for late payments. (−) Order has an extra state; authorizations expire (PAY-7), so a long delay between steps needs reconciliation.

ADR-E13 — Refund is an entity inside Payment; Dispute is its own aggregate

Status: accepted.

Decision: PAY-4 (refunds never exceed captured) is a true invariant, so refunds live in the payment's consistency boundary. A dispute has its own lifecycle, deadlines and external driver, and affects the payment eventually through an event.

Consequences: (+) Concurrent refunds are safe through the version check. (−) A payment with many refunds loads them all (acceptable: the count is small). Revisit if refunds become initiated by many independent parties.

ADR-E14 — Fraud: the vendor supplies a signal; our policy decides

Status: accepted.

Decision: A fraud context owns RiskAssessment and a RiskPolicy domain service. Vendor scores and verdicts are inputs. Unavailability is handled by an explicit, configurable, tested fail-open/fail-closed policy that depends on order value. Screening is a saga step behind an Open Host Service, switchable off.

Consequences: (+) Business risk appetite is testable and vendor-independent. (+) An outage has a defined behaviour. (−) We duplicate a small amount of decision logic the vendor also has; that's the price of owning the decision.

ADR-E15 — Outbound vendor feedback uses a durable work queue

Status: accepted.

Decision: Events are translated into TransactionOutcomes and stored in a queue table (written with the consumer's inbox row), then delivered by a worker with retry, backoff, per-transaction ordering, idempotent ids and a dead-letter state. Reporting never sits in a customer-facing request path.

Consequences: (+) A vendor outage costs nothing but delay. (+) Same reliability story as the outbox. (−) One more worker and table to operate; dead-letters need an owner.

ADR-E16 — Every chargeback is accepted on arrival; defence is deferred

Status: accepted (revisit when chargeback losses justify a defence, E5.14).

Decision: When a dispute opens, Payments accepts it with the provider, marks the payment ChargedBack, and publishes dispute_accepted.v1. Ticketing voids the order's tickets and refunds nothing. The customer's identifiers are denylisted (ADR-E17).

Consequences: (+) No evidence workflow, no deadlines to miss, and a much smaller first version. (+) The Dispute aggregate already has the states a defence will need. (−) We lose every dispute, including the ones we would have won. (−) A customer who is wrongly blocked needs staff to lift the entry.

ADR-E17 — A Denylist context; each context checks the identifiers it owns

Status: accepted.

Context: A chargeback must stop the customer from buying again by account, email and card, and those identifiers belong to Ticketing, Identity and Payments respectively.

Decision: A small generic denylist context stores blocked (kind, value) identifiers with reasons and history, and publishes a synchronous Check (an Open Host Service, as in ADR-E10). It fills itself from events (order_charged_back; later confirmed fraud) and keeps a customer → email projection. Ticketing checks the customer before holding seats; Payments checks the card fingerprint before authorizing. Card tokens are never blocked, only provider fingerprints. Emails are stored as keyed hashes.

Consequences: (+) New identifier kinds and new reasons to block don't touch the contexts that check. (+) No context depends on another's model. (−) One more synchronous dependency on the purchase path, which fails closed. (−) Blocking by card or email can catch innocent people who share them; lifting is a manual, audited staff action.
