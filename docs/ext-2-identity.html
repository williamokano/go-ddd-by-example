Extension track · E2 · needs Part 4

Identity & access

Until now anyone can call anything. You'll add a small identity module of your own (local username/password and room for any number of SSO providers), then enforce what each person may do. The point is where each piece lives in the hexagon: authentication at the edge, coarse authorization around the use cases, fine-grained rules in the domain.

The shape of the solution

Authentication and authorization are cross-cutting: every context needs the answer, but none of them should own the machinery. The trick is to separate three questions that are easy to blur together:

QuestionNameWhere it livesWhy there
Who is this?AuthenticationDriving adapter (HTTP middleware) → Principal in contextIt's about the transport (headers, cookies, tokens). A use case shouldn't know how the caller proved who they are.
May this kind of actor do this kind of action?Authorization, coarse (RBAC)A decorator around each use case, assembled in the composition rootThe check is the same shape for every use case, so it doesn't belong in any one of them, and the use-case tests don't need to change.
May this actor do this to this thing?Authorization, fine-grained (ownership)Domain / use caseIt depends on business data ("is this user the venue's manager?"), which only the model knows.
Request:
 HTTP ─► authn ─► Principal ─► authz decorator ─► use case ─► aggregate
         (driving   (platform/ (RBAC: permission)    (ownership: VEN-8)
          adapter)   actor)

Login:
 credentials ─► IdentityProvider ─► verified identity ─► link to local User
                (password | oidc:google | oidc:entra | ...)        │
                                                                   ▼
                                                  TokenIssuer ─► our own signed token
Design decisions (ADR-E05, ADR-E06, ADR-E07)

Principal is a plain value in internal/platform/actor (stdlib only). Application layers may import it; the domain may not. When the domain needs "who", the use case passes a plain id in (venue.ManagedBy(userID)), the same way time and ids are inputs (ADR-008). Identity is its own bounded context (internal/identity) with a Users table and its own login use cases; other contexts only ever see a UserID and a set of permissions.

E2.1 Principal, permissions and roles

Goal
Define the vocabulary of "who" and "what may they do", with no I/O.
Rules
AUTH-1, AUTH-2
Creates
internal/platform/actor/{principal,permission,errors}.go (the Principal, the Permission string type, ErrForbidden), internal/identity/domain/role.go (which role grants which permissions) + tests
IdRule
AUTH-1A Principal is either a user (UserID + permissions) or a system actor ("scheduler", "payments-webhook"). Anonymous is its own explicit value, never nil.
AUTH-2Permissions are resource:action strings (venue:register, show:publish, order:refund, audit:read). Roles are named sets of permissions. Code checks permissions, never role names.
TDD script
  1. A user principal reports Can(perm) true only for permissions it holds; Anonymous.Can(x) is always false.
  2. actor.From(ctx) on a context with no principal returns Anonymous (not a panic, not nil); actor.With(ctx, p) round-trips.
  3. The built-in role table: Customer has order:place but not venue:register; VenueManager has venue:register and venue:manage (which venues is VEN-8's job, not RBAC's); Promoter has show:draft and show:publish; Staff has order:refund and audit:read.
  4. A user with several roles gets the union of permissions.
  5. Unknown role name from storage → error (don't silently grant nothing, and don't silently grant everything).
Discuss

Why "check permissions, not roles"? What breaks when a rule is written if p.HasRole("staff") and the business invents "Senior Support" next quarter?

E2.2 The User aggregate and local credentials

Goal
Model a user, and keep "how they prove themselves" separate from "who they are".
Rules
AUTH-3, AUTH-4
Creates
internal/identity/domain/{user,email,credential}.go, application.PasswordHasher port, an in-memory fake hasher
IdRule
AUTH-3A user has a unique, normalised (trimmed, lower-cased) email, a status (Active/Disabled) and a set of roles. A disabled user can never authenticate, via any source.
AUTH-4A user may have several credentials of different kinds: a password hash, and/or any number of external identities (issuer, subject). The user aggregate does not know how any of them is verified.
TDD script
  1. NewEmail normalises and rejects malformed addresses; Email is a value object (equality by value).
  2. RegisterUser(id, email, roles, now) records UserRegistered; a new user is Active with the Customer role by default.
  3. Disable() / Enable() and their idempotence.
  4. LinkExternalIdentity(issuer, subject): linking the same pair twice is a no-op; linking a pair another user already owns is rejected at the application layer (uniqueness lives in the repository, as with TKT-3).
  5. SetPassword(hash) accepts only a PasswordHash value, never a plain string, so the domain can't store a plaintext password by accident.
Pitfall

Hashing is infrastructure. The domain holds an opaque PasswordHash; the PasswordHasher port (Hash, Verify) is declared in application and implemented later with argon2id (golang.org/x/crypto/argon2). Don't write your own scheme, and don't use a fast hash (SHA-256, MD5) for passwords. A fake hasher in tests keeps them fast.

E2.3 Login use cases and the IdentityProvider port

Goal
One login use case that works for any identity source, so adding Google or Entra later doesn't change it.
Rules
AUTH-5, AUTH-6
Concepts
Strategy pattern, ports & adapters, driven ports
IdRule
AUTH-5Every identity source reduces to the same output: a VerifiedIdentity{Issuer, Subject, Email?, EmailVerified}. The Login use case passes the proof through without ever inspecting it: it never reads a password, parses a JWT from Google, or knows what a SAML assertion is.
AUTH-6Login failure responses are indistinguishable: unknown user, wrong password and disabled account all return ErrInvalidCredentials. (No account enumeration.)
// internal/identity/application/ports.go (a sketch to design from, not to copy)
type IdentityProvider interface {
    Name() string  // "password", "oidc:google", ...
    Authenticate(ctx context.Context, proof Proof) (VerifiedIdentity, error)
}
// Proof is provider-specific ({"email","password"} or {"id_token"});
// opaque to the use case.
type Proof map[string]string
Your turn
  1. Declare IdentityProvider, TokenIssuer (Issue(Claims) (Token, error)) and UserRepository in identity/application.
  2. Write Login as a use case that takes a provider name and a Proof, looks the provider up in a registry, resolves the VerifiedIdentity to a User, and issues a token.
  3. The "password" provider is itself an adapter (identity/adapters/driven/password): it looks the user up by email, runs the hasher, and returns a VerifiedIdentity with Stagehand as the issuer. Write it against fakes.
TDD script
  1. Login with the right password → a token for that user's UserID.
  2. Wrong password, unknown email, disabled user → the same error (AUTH-6). Add a test that the password provider still calls the hasher for an unknown email, so timing doesn't leak existence.
  3. Unknown provider name → ErrUnknownProvider.
  4. A fake second provider ("fake-sso") logs in a linked user without any change to Login. This test is the point of the lesson.
  5. Token claims are minimal: subject, expiry, a token id. Permissions are looked up per request or embedded with a short expiry (see Discuss).
Discuss

Embedded permissions make requests cheap but go stale: a fired employee keeps access until the token expires. Per-request lookup is always fresh but costs a read. Which would you start with, and what is the smallest mitigation for the other?

E2.4 Persistence and the token adapter

Goal
Postgres-backed users and a real signed token, following the same moves as Part 3.
Creates
db/migrations/0000N_identity.sql (identity schema: users, user_roles, external_identities with UNIQUE (issuer, subject)), db/queries/identity/*.sql, identity/adapters/driven/postgres, identity/adapters/driven/token (JWT or PASETO); a stagehand users add --email … --role staff subcommand
Your turn
  1. Write the migration and queries; reuse the repository contract suite idea from 2.6 for UserRepository and run it against both the fake and Postgres.
  2. Write the token adapter: sign with a key from config, set exp, iat, jti, aud, iss; on verify, pin the algorithm and reject alg: none and algorithm switches.
  3. Add a unique-violation to domain-error mapping for duplicate email, as you did for optimistic concurrency in 3.6.
  4. Public sign-up only ever creates Customers. Add a users add subcommand (next to serve and migrate) to bootstrap the first Staff user, and use it in the e2e setup.
Pitfall

Key handling is configuration, not code: the signing key comes from an environment variable or file, rotates by supporting a kid and verifying against more than one key, and is never logged or committed. Write the "expired token", "tampered token" and "wrong audience" tests first.

E2.5 The authentication middleware (a driving adapter)

Goal
Turn an Authorization: Bearer … header into a Principal in the request context, and nothing more.
Rules
AUTH-7
Creates
platform/httpx/authn.go (the middleware, plus a small TokenVerifier interface it consumes, implemented by identity's token adapter and wired in cmd/stagehand); identity/adapters/driving/httpapi with POST /auth/login and GET /auth/me
IdRule
AUTH-7Missing or invalid credentials on a protected route → 401. Valid credentials but insufficient permission → 403. Never the other way round, and never leak why a token was rejected.
TDD script
  1. No header → the handler runs with Anonymous in context (the middleware identifies; it does not decide). A separate httpx.Authenticated(h) wrapper turns Anonymous into 401 on protected routes.
  2. Valid token → the downstream handler sees the right Principal.
  3. Expired / tampered token → 401 with a generic body.
  4. POST /auth/login with a provider name and proof → token; same status and body shape for all failure causes (AUTH-6).
  5. Health and metrics endpoints stay public (an explicit allow-list, not an accident).
  6. Every context's error table (4.2) maps actor.ErrForbidden to 403.
Discuss

The middleware is in the adapter, but actor.Principal is in platform. Draw the import arrows. What would go wrong if the use cases imported net/http to read the header themselves? Which of the two is tested more cheaply?

E2.6 RBAC as a decorator: protect every use case without editing one

Goal
Enforce coarse permissions across Venue, Show and Ticketing by wrapping use cases in the composition root.
Rules
AUTH-8
Concepts
Decorator pattern, composition root
IdRule
AUTH-8Each use case declares the single permission it requires. A denied call returns ErrForbidden before any domain code runs and before any state is loaded.
// internal/platform/authz: one generic decorator for every use case that
// returns a result. The handlers already have this shape (chapter 3).
type handler[C, R any] interface {
    Handle(ctx context.Context, cmd C) (R, error)
}

type Authorized[C, R any] struct {
    perm actor.Permission
    next handler[C, R]
}

func Require[C, R any](perm actor.Permission, next handler[C, R]) Authorized[C, R] {
    return Authorized[C, R]{perm: perm, next: next}
}

func (a Authorized[C, R]) Handle(ctx context.Context, cmd C) (R, error) {
    if !actor.From(ctx).Can(a.perm) {
        var zero R
        return zero, actor.ErrForbidden
    }
    return a.next.Handle(ctx, cmd)
}
// Use cases whose Handle returns only error (AddSection) need a twin, RequireCmd.
Your turn
  1. Write the decorator test-first with a stub use case. Then wrap RegisterVenue, PublishShow, PlaceOrder and the rest in cmd/stagehand. The HTTP adapters don't notice: their one-method interfaces (chapter 3, "Driving ports in Go") accept the decorated handler as they accepted the plain one.
  2. Do not open any existing use-case file. If you feel you must, write down why: that's a design smell worth discussing.
  3. One change you can't avoid: today the HTTP adapters trust the X-Customer-ID and X-Actor-ID headers (chapter 1), so anyone can act as anyone. Take the ids from the principal instead and stop reading those headers. That's a change to the driving adapters, which is exactly where it belongs: the commands still receive a customer id, they just get a trustworthy one.
  4. One thing that does not change: the contact email on POST /orders (TKT-6). Identity owns the account email, the address you log in with; the order owns the contact email, the address the tickets go to. They are different concepts that often hold the same value (someone buying for a friend uses the friend's address). The checkout page may pre-fill the contact email from the account, but Ticketing never reads Identity's data.
  5. Run the existing suite. Domain, application and adapter tests pass untouched, because they build use cases without the decorator. The e2e suite now gets 401s: give it a login helper (one user per role, created with users add) and send tokens. That is the honest cost of the feature.
  6. Add one e2e test per role showing which of the three journeys (S1, S3, S6) each can and can't run.
Pitfall: the forgotten route

With decoration in the composition root, a new use case is unprotected until someone wraps it. Add an architecture test: every handler registered on the router must be built through Require(...) or be on an explicit public list. Make forgetting loud.

E2.7 Ownership: a rule that needs business data

Goal
"A venue manager may only change venues they manage." Extend the existing Venue aggregate without breaking it.
Rules
VEN-8
Touches
venue/domain (additively), the RegisterVenue command, one guard line in AddSection, ActivateVenue and RetireVenue, a nullable manager_id column. No contract changes: no other context needs to know who manages a venue.
IdRule
VEN-8A venue is managed by one user (ManagerID, set at registration to the registering user). Only its manager, or a principal with venue:admin, may add sections, activate or retire it.
TDD script
  1. RegisterVenue gains a ManagerID input. Test helpers that build a venue get one more argument; no behaviour test changes its assertions.
  2. venue.ManagedBy(userID) bool: true only for the manager. The domain answers the question; it doesn't know about permissions or admins.
  3. Application: AddSection by a non-manager → ErrNotVenueManager and nothing saved; by the manager → OK; by a principal with venue:admin → OK. Same for activate and retire. This is the one place E2 opens existing use cases, and each gets a single guard after the load.
  4. RegisterVenue takes the manager from the principal, never from a header or the request body.
  5. Venues created before this change have no manager. Decide what that means (only admins may change them) and test it, including reconstitution from a row with a NULL manager_id.
Why not put the check inside AddSection itself?

You could: venue.AddSection(by, section) would make the rule impossible to forget, at the price of changing every behaviour method's signature and every test that calls it. The admin bypass would still have to live outside, because the domain doesn't import actor. Try both on paper and choose. The lesson is that either way the knowledge of who manages the venue sits in the aggregate, and the knowledge of permissions sits in the application.

Discuss

Could RBAC alone express this rule? ("manager of which venue?") Where would "permissions per resource" tempt you to put business data in the identity context, and why is that a leak between contexts?

E2.8 A second source: SSO through OpenID Connect

Goal
Add "Sign in with an external IdP" as a new IdentityProvider adapter. Local password login keeps working alongside it.
Rules
AUTH-9, AUTH-10
Creates
identity/adapters/driven/oidc (one generic adapter configured per provider), config for N providers, a fake IdP for tests
IdRule
AUTH-9An external identity is identified by (issuer, subject), never by email alone. The first successful login with an unknown pair either auto-provisions a Customer user or is rejected, per config.
AUTH-10An external identity may be linked to an existing user by email only when the provider asserts email_verified and the provider is configured as trusted for linking. Otherwise it creates a separate user.
Your turn
  1. Implement one oidc adapter that validates an ID token: signature against the provider's JWKS, iss, aud, exp, and nonce when used. Configure it per provider (google, entra, …) from a list in config. Adding a provider is a config change.
  2. Test it with an in-process fake IdP (httptest.Server serving a discovery document and a JWKS you sign with a test key). No real network.
  3. Register both password and oidc:* providers in the registry at startup; each can be disabled by config. Test the matrix: password off / oidc on, and the reverse.
  4. The browser flow (redirect, code exchange) is a driving-adapter concern. Keep it out of Login: by the time we reach the use case, we hold a verified ID token.
Pitfall: account takeover by email

If you link by email without email_verified and trust, an attacker who creates an account at a lax provider with your email becomes you. AUTH-10 exists because of that. Write the attack as a test first.

Discuss

You added a whole new authentication mechanism and changed zero lines of Login, User, the token issuer, the middleware or any other context. Which design choice made that true? What would have broken it?
