Reference · Chapter 2

DDD building blocks

What each concept is, how to recognise it in Stagehand, how to write it in idiomatic Go, and the mistakes to avoid. Lessons link here when they introduce a concept.

Strategic vs tactical DDD

DDD has two halves:

  • Strategic design decides what to model and where the boundaries are: ubiquitous language, subdomains, bounded contexts, context maps. Chapter 1 is our strategic design. This half matters most: a perfect aggregate inside the wrong boundary is still wrong.
  • Tactical design is the patterns for writing the model inside one context: entities, value objects, aggregates, domain events, domain services, repositories, factories. That's this chapter.

Ubiquitous language

The business words, used everywhere: in conversations, docs, tests, type names, method names, event names. If the business says "hold seats", the method is inventory.Hold(...), not inventory.Reserve(...) or SetSeatStatus(seat, 2). When you notice you're translating between what people say and what the code says, rename the code.

PitfallCRUD verbs (UpdateShow, SetStatus) in a domain model are a smell. The business never says "update the show status to 3". It says "publish the show" or "cancel the show". Model the intention, not the data change.

Value object

An object defined entirely by its attributes. It has no identity: two Money{1500, EUR} are interchangeable, just as two €10 notes are. Value objects are:

  • Immutable. Operations return a new value (a.Add(b) returns a new Money).
  • Self-validating. You can't build an invalid one. The constructor is the only way in.
  • Compared by value. In Go, a struct of comparable fields gets == for free.

Stagehand examples: Money, Address, SectionCode, Row, Schedule, PriceList, SeatRef, TicketCode, and all the typed IDs.

package domain

// SectionCode identifies a section within a venue, e.g. "ORCH" or "BAL-L".
type SectionCode struct{ value string }   // unexported field ⇒ only the constructor can build one

func NewSectionCode(raw string) (SectionCode, error) {
	v := strings.ToUpper(strings.TrimSpace(raw))
	if !sectionCodePattern.MatchString(v) {
		return SectionCode{}, fmt.Errorf("%w: %q", ErrInvalidSectionCode, raw)
	}
	return SectionCode{value: v}, nil
}

func (c SectionCode) String() string { return c.value }   // value receiver: VOs are copied freely
Why bother? ("parse, don't validate")

When a function takes a SectionCode instead of a string, the type system proves the value was validated. Validation happens once, at the edge, and the rest of the code can trust its inputs. Primitive obsession (strings and ints everywhere) spreads validation thin and loses meaning.

Go pitfall: the zero value

In Go, anyone can write SectionCode{} and skip your constructor. You can't fully prevent this. Mitigate it: keep fields unexported (so outside packages can only make the empty zero value), give the VO an IsZero() method, and have aggregates reject zero values passed in. Go has no private constructors, so be explicit about it.

Entity

An object with an identity that persists while its attributes change. A section is still "the ORCH section" after you rename it. Two entities are equal when their IDs are equal, whatever their attributes.

  • Stagehand: Section (inside Venue, identified by SectionCode, a local identity that only has to be unique within its venue) and Hold (inside ShowInventory). Aggregate roots are entities too.
  • In Go, use pointer receivers for methods that mutate, and unexported fields with getter methods. Don't write setters. Write behaviour methods named after the business operation.
Entity or value object?

Ask: "If two of these had identical attributes, would the business consider them the same thing?" Two identical rows "A, 20 seats" in the same section is a duplicate (an error), and a row has no life of its own, so Row is a VO. Two holds with identical seats at different times are different holds, so Hold is an entity.

Aggregate and aggregate root

An aggregate is a cluster of entities and value objects that has to stay consistent as a unit. One entity in the cluster is the aggregate root, the only object the outside world may hold a reference to or call.

   ┌─────────────────────────── Venue aggregate ────────────────────────────┐
   │                                                                         │
   │   Venue  ◀── aggregate ROOT (entity, global identity VenueID)           │
   │    │  name: string, address: Address (VO), status: Status              │
   │    │                                                                    │
   │    ├── Section "ORCH" (entity, local identity SectionCode)             │
   │    │     rows: [Row{A,20}, Row{B,22}] (VOs)                            │
   │    └── Section "FLOOR" (entity) kind: GA, capacity: 500                 │
   │                                                                         │
   └─────────────────────────────────────────────────────────────────────────┘
   Outside code calls venue.AddSection(...), never section.AddRow(...) directly.

Why is the root the root?

Because invariants span the whole cluster, and only an object that sees the whole cluster can enforce them. "Section codes are unique within a venue" (VEN-2) can't be checked by a Section, because a section doesn't know about its siblings. "No layout changes once Active" (VEN-4) depends on the venue's status. If outside code could get hold of a *Section and change it, it could bypass both rules. So:

  1. The root is the single entry point. Every change goes through a method on the root, which checks the invariants before and after.
  2. The root controls access. Internals are returned as copies or read-only views, never as mutable pointers.
  3. The root has the global identity. Inner entities only need identity that's unique within the aggregate.

The four rules of aggregate design (Vaughn Vernon)

  1. Model true invariants inside consistency boundaries. An aggregate exists to protect rules that must hold immediately after every change, not "eventually".
  2. Design small aggregates. Big aggregates mean more lock contention, slower loads and more conflicts.
  3. Reference other aggregates by ID only. Show stores a VenueID, never a *Venue. That makes the boundary explicit and keeps loading cheap.
  4. Use eventual consistency outside the boundary. One transaction modifies one aggregate. Changes to other aggregates react to domain events.
Why "one aggregate per transaction"?

An aggregate is a unit of consistency, so it's also the unit of concurrency control (optimistic locking with a version number). If one transaction modifies two aggregates, it has to win both locks. Contention then compounds, and your boundary hasn't actually protected anything. The rule pushes us toward events and sagas, which is what Part 7's checkout does. You'll see the trade-off first-hand.

The big design question in Stagehand

Is "a seat is never sold twice" (TKT-5) protected by one ShowInventory aggregate per show, by one aggregate per section, or by one per seat? Each answer has a cost. One per show is simple and fully consistent, but it serialises every hold on a busy show. One per seat scales, but then "hold 4 seats atomically" spans 4 aggregates. We start with one per show (ADR-005) and revisit it in Part 9.

What Part 9.1 decided (ADR-013): one SectionInventory per show and section. A hold already lived in one section, so TKT-5 stays inside one aggregate. The price: TKT-3 weakens to "one hold per section", and "the show is sold out" needs a domain service (ShowSoldOut) over all sections.

Domain event

Something that happened in the domain that domain experts care about. It's named in the past tense (SeatsHeld, ShowCancelled), immutable, and carries the data needed to understand it (IDs, the relevant values, OccurredAt).

  • The aggregate records events as a side effect of its behaviour methods. It doesn't publish them, because it knows nothing about Kafka.
  • After the aggregate is persisted, the events are pulled from it (PullEvents() returns them and clears the list) and written to the outbox in the same database transaction.
  • Tests assert on events: "when I activate the venue, a VenueActivated event is recorded". Testing behaviour through events is more robust than poking at internal state.
// sharedkernel (after Part 7's extraction; before that it lives in venue/domain)
type DomainEvent interface {
	EventName() string        // e.g. "venue.VenueActivated"
	OccurredAt() time.Time
}

type Events struct{ pending []DomainEvent }   // a named field in aggregate roots: v.events.Record(…)

func (e *Events) Record(ev DomainEvent)      { e.pending = append(e.pending, ev) }
func (e *Events) PullEvents() []DomainEvent  { out := e.pending; e.pending = nil; return out }
Go pitfall: don't embed the recorder

Embedding Events in Venue would promote its exported Record method onto *Venue, so any caller could do venue.Record(VenueRetired{…}) and fake the aggregate's history. Keep it as an unexported field and expose only PullEvents() on the root.

Domain events vs integration events: a domain event is internal to a context and may change freely. An integration event is a public contract (Published Language), versioned, and translated from domain events at the boundary. See Chapter 4.

Domain service

Domain logic that doesn't naturally belong to a single entity or value object, usually because it needs several aggregates or a concept that isn't a thing. It is:

  • Named in the ubiquitous language (SchedulingPolicy, not ShowHelper).
  • Stateless, and in our codebase pure: no I/O. The application layer loads what it needs and passes it in.
  • Stagehand example: SchedulingPolicy.EnsureNoOverlap(candidate Schedule, existing []Show) error implements SHW-3. No single Show knows about the other shows at the venue.
  • Found in Part 9: once the inventory is cut per section (ADR-013), "is the show sold out?" belongs to no single SectionInventory. ShowSoldOut answers it from all of them. And an order's total depends on its lines, Stagehand's fee rules and the venue's country: PricingPolicy computes the breakdown and the Order records it. Its fee rules are specifications (SeatsAtLeast(6), InSection("VIP"), combined with And/Or/Not), so a new rule is a new line of data, not a new branch.
PitfallIf every rule ends up in services and your entities are bags of getters and setters, you have an anemic domain model. Try the entity first. Use a domain service only when the logic really doesn't fit any single object.

Application service (use case)

The coordinator of one use case. It contains no business rules. Its job is a fixed recipe:

  1. Receive a command (a plain struct of primitives/DTOs).
  2. Parse the input into domain types (value objects).
  3. Load the aggregate(s) through a repository port, and get the time from the Clock port and new IDs from the IDGenerator port.
  4. Call one behaviour method on the aggregate (or a domain service).
  5. Save the aggregate. Its events go to the outbox atomically.
  6. Return a result (an ID or a DTO, never the aggregate itself).

It also owns the cross-cutting application concerns: the transaction boundary, authorisation checks ("is this actor the promoter of this show?"), idempotency keys, logging and metrics.

The litmus test

"Would this rule still exist if Stagehand sold tickets with paper forms and a phone line?" If yes, it's domain: a seat can't be sold twice, holds expire. If it only exists because of software ("load from DB, then save, then commit"), it's application or infrastructure.

Repository

A collection-like abstraction for loading and saving whole aggregates. There's one repository per aggregate root, not one per table. VenueRepository saves the venue with its sections, even though they live in two tables.

// internal/venue/application/ports.go — a DRIVEN port
type VenueRepository interface {
	Get(ctx context.Context, id domain.VenueID) (*domain.Venue, error) // ErrVenueNotFound
	Save(ctx context.Context, v *domain.Venue) error                    // insert or update, optimistic lock, writes outbox
}
  • The interface is defined by the consumer (the application layer). The implementation is an adapter (adapters/driven/postgres). This is dependency inversion: the core doesn't depend on Postgres; Postgres depends on the core's interface.
  • Keep repositories small: Get, Save, and only the finder methods a use case actually needs. Screens and lists use the query side (read models), not repositories.
Where should repository interfaces live? (decision)

Evans puts repository interfaces in the domain layer. Many hexagonal codebases put all driven ports in the application layer. We put them in application, which keeps the domain 100% pure: no interfaces to infrastructure, no context.Context, nothing to fake in domain tests. A domain service that "needs" a repository gets the data passed in by the application service instead. See ADR-002.

Factories, constructors and reconstitution

There are two different ways to bring an aggregate into memory, and you must keep them apart:

  • Creation (domain.RegisterVenue(id, name, addr, now)): validates everything, sets the initial state, and records a creation event. Name it with the business verb if one exists.
  • Reconstitution (domain.RehydrateVenue(snapshot)): used only by repositories to rebuild an aggregate from storage. It does not record events (nothing new happened) and trusts the data it gets (it was valid when it was saved).
PitfallDon't export a big NewVenue(all, fields, ...) that both creates and reconstitutes. Repositories would emit "VenueRegistered" every time they load. Use two functions with two names and two jobs.

Policies, process managers and sagas

  • Policy (event-storming lilac sticky note): "whenever X happens, then do Y". Example: "whenever a venue is retired, cancel its future shows" (SHW-7). In code it's an event handler that calls a use case.
  • Saga / process manager: a long-running business process across several aggregates or contexts, driven by events, with compensating actions when a later step fails. Stagehand's checkout is one: OrderPaid → ConfirmHold → (SeatsSold → IssueTickets) | (HoldConfirmationFailed → RefundOrder). We start with choreography (each step reacts to the previous event). The alternative is orchestration (a stateful coordinator that decides the next step). Part 9.4 builds it, CheckoutProcess, a small aggregate whose state is "where is this order in the flow"; the code keeps both, switched by SAGA_STYLE (ADR-014).
  • Clock-driven policy: "when time T passes, do Y" has no triggering event. A scheduler asks the repository for what is due and calls a use case: hold expiry (TKT-4) and show completion (SHW-9).

Shared kernel

A small, explicitly shared subset of the domain model that two or more contexts agree to use identically and to change only together. Ours: Money and Currency (every context means exactly the same thing by €15.00), plus the tiny domain-event building block.

Shared kernel is NOT a "common" / "utils" package
  • It contains domain concepts, not technical helpers. Database helpers, the Kafka client, config and logging live in internal/platform, which is technical plumbing, not part of any model.
  • It must stay tiny and stable. Every change hits every context. If you want to add Seat to it, stop: that word means three different things (Chapter 1).
  • It earns its place by emerging. In Part 6 Show writes its own Money. In Part 7 Ticketing needs the identical concept, and we deliberately promote it. Duplication first, extraction once the need is proven.

Domain errors

Business rule violations are expected outcomes, not crashes. Model them as exported sentinel errors (or small typed errors when they carry data) in the domain package:

var (
	ErrVenueNotDraft        = errors.New("venue: layout can only change while draft")   // VEN-4
	ErrDuplicateSectionCode = errors.New("venue: duplicate section code")               // VEN-2
)

// Wrap with context, test with errors.Is:
return fmt.Errorf("%w: %s", ErrDuplicateSectionCode, code)

The HTTP adapter maps them to status codes (validation → 422, not found → 404, conflict/state → 409). The domain never knows about HTTP.
