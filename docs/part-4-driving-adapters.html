4.1 HTTP plumbing in platform/httpx

Goal
Small, tested helpers so context adapters stay tiny: decode JSON strictly, write JSON, write errors as RFC 9457 application/problem+json.
Creates
internal/platform/httpx/json.go, problem.go, middleware.go (request ID, recover, slog access log)
TDD script
  1. DecodeJSON rejects unknown fields and bodies over 1 MiB with a 400 problem.
  2. WriteProblem(w, status, title, detail) sets the content type and body.
  3. The recover middleware turns a panic into a 500 problem and logs it.
Discuss

Why does this live in platform and not the shared kernel? (It's technical, not domain. Chapter 2, Shared kernel.)

4.2 The Venue HTTP adapter

Goal
Translate HTTP ↔ use cases and nothing more. All decisions stay in the core.
Concepts
Driving adapter, driving ports in Go
Creates
internal/venue/adapters/driving/httpapi/{routes,handlers,dto,errors}.go + tests
RouteUse caseSuccess
POST /venuesRegisterVenue201 + Location
POST /venues/{id}/sectionsAddSection204
POST /venues/{id}/activationActivateVenue204
POST /venues/{id}/retirementRetireVenue204
GET /venues/{id}VenueQueries.Get200

Error mapping (one table in errors.go): invalid input (ErrInvalid*) → 422; ErrVenueNotFound → 404; state or duplicate violations → 409; ErrConcurrentModification (after retries) → 409; anything else → 500, logged.

TDD script (httptest + stub use cases)
  1. POST /venues with valid JSON calls the use case with the mapped command, then returns 201 and a Location header.
  2. Malformed JSON → 400, and the use case is not called.
  3. Table: each domain/application error → the expected status and problem title.
  4. GET /venues/{id} renders the VenueView as the response JSON (compare against a golden file).
Pitfall

Using domain.Venue as the JSON response type ties your public API to your model, and every internal rename becomes a breaking API change. Keep separate DTOs.

Discuss

Why POST /venues/{id}/activation rather than PATCH /venues/{id} {"status":"active"}? (Ubiquitous language and intention, from Chapter 2.)

4.3 Composition root: stagehand serve

Goal
One readable function that builds the whole object graph and runs it with graceful shutdown.
Creates
internal/platform/config; cmd/stagehand/serve.go
Your turn
  1. A typed config.Load() from env vars (Chapter 6 table), with a unit test for defaults and invalid values.
  2. serve: signal.NotifyContext → pool → repositories → handlers → routes → http.Server → Shutdown with a timeout on cancel.
  3. A slog JSON handler at the configured level.
Why no DI framework?

The wiring is about 40 explicit lines. You can read in one screen what talks to what, and the compiler checks every dependency. A container would hide the architecture you're trying to learn.

4.6 The architecture test

Goal
Turn Chapter 3's import table into a failing test.
Creates
internal/archtest/archtest_test.go
TDD script
  1. Load ./internal/... with go/packages (non-test imports only). */domain may import only stdlib, sharedkernel and google/uuid.
  2. */application may not import adapters, platform, pgx or franz-go.
  3. No package in context A imports context B, except B/contracts.
  4. platform imports no context.
  5. Prove that it works: add a forbidden import, watch it fail, and remove it.

Done when

  • The Venue context is complete end-to-end (minus events), and the architecture is enforced by CI.
