Course · Part 9

Stretch goals

Independent exercises. Do them in any order. Each one tests whether the architecture really makes change cheap.

9.1 Re-cut the inventory aggregate per section

Supersede ADR-005: a SectionInventory per (show, section), with holds limited to one section. Re-run the 7.6 measurements and compare. Which tests had to change? (Ideally domain tests and the inventory repository. HTTP and e2e should barely change.)

9.2 Ticket check-in at the gate

A new use case: CheckIn(ticketCode, gateID, now). A ticket can only be checked in once, only if it isn't voided, and only on the day of the show. It touches only the Ticket aggregate. Notice how cheap that is, because Ticket was kept small.

9.3 Contract evolution: show.published.v2

Add per-seat accessibility flags, which requires restructuring the payload. Publish v1 and v2 side by side, migrate Ticketing to v2, then retire v1. Golden tests guide you through it.

9.4 Orchestration instead of choreography

Re-implement checkout with an explicit Checkout process-manager aggregate (a state machine that issues commands). Compare readability, testability and failure handling with ADR-010.

9.5 Show lifecycle completion and back-on-sale

A scheduler marks shows Completed after endsAt. When a refund frees seats on a SoldOut show, Ticketing publishes inventory_available_again and Show moves back to Published.

9.6 Database-enforced boundaries

One Postgres role per context, with privileges only on its own schema, and each context's pool connects with its own role. Try a cross-schema query and watch the database refuse it.

9.7 Distributed tracing with OpenTelemetry

Replace the hand-rolled correlation IDs with OTel spans propagated through Kafka headers. Add Jaeger to Compose. Which layers needed changes? (Only adapters and platform.)

9.8 Fees and taxes as a domain service

The order total now includes a service fee (a percentage with a minimum) and VAT by venue country. Where does this logic go? Model it as a PricingPolicy domain service, with the specification pattern for fee rules.
