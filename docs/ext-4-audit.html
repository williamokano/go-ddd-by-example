Audit trail: who did what, and when

With real users (E2) we can finally answer "who retired that venue?" and "who refunded that order?". An audit trail is not a log file: it's a durable, queryable, tamper-resistant record that the business, support and sometimes regulators rely on. You'll build it from two complementary sources, and compare them.

Two ways to know "who did what"

A · Command-level (decorator)B · Integration events + actor
RecordsThe attempt: actor, command name, target, outcome (succeeded / denied / failed)The published facts, attributed to whoever caused them
Sees denied and failed attempts?Yes (security-relevant)No: nothing happened, so no event
Sees changes that never become integration events?YesNo. VenueRegistered and SectionAdded never leave Venue (5.3)
Sees system-initiated changes (expiry, policies reacting to other contexts)?Only if they run through decorated use cases with a system principalYes, with the causing event
Domain model changes?NoneNone; the actor travels as envelope metadata
Design decision (ADR-E09)

We do both, and neither touches an aggregate. The important constraint is ownership: each context owns its schema, and a Venue transaction must not write into an audit table. So the decorator writes an audit record into the acting context's own outbox, in the same transaction as the change (8.4's TxManager makes that possible). The relay publishes it to an audit.records topic, and the audit context consumes it, together with the actor-stamped integration events, into an append-only store. It's the outbox pattern from Part 5, reused for a new kind of message.

E4.1 Decide what belongs in the trail

Goal
Write the rules before the code.
Rules
AUD-1, AUD-2, AUD-3
IdRule
AUD-1Every entry records: when, actor (user id or system name), action (a stable name, e.g. venue.retire), target (type + id), outcome (succeeded, denied, failed), requestId/correlationId, and the client IP when there is one.
AUD-2Entries are immutable and append-only. There is no update or delete path in the application, and the application's database role has no UPDATE/DELETE privilege on the table.
AUD-3Entries never contain secrets or sensitive personal data: no passwords, tokens, full card data, or free-text bodies. Store identifiers and the names of changed fields, not full before/after documents, unless a rule says otherwise.
Your turn (paper first)
  1. List ten actions in Stagehand that must be auditable (hint: anything money-, access- or lifecycle-related) and five that need not be.
  2. For each, decide: command-level, event-level, or both?
  3. Who reads this data (support, a manager, an auditor), and what question will each ask? Design the query shape from those questions.

E4.2 The audit entry, a port and an append-only table

Goal
A small audit context: entry value object, AuditLog port, fake, Postgres adapter.
Creates
internal/audit/{domain,application,contracts} (the contract is the audit.command_attempted.v1 record every context publishes), db/migrations/0000N_audit.sql, the Postgres adapter
TDD script
  1. NewEntry(...) validates (non-empty actor, action, target) and stamps time from the injected clock (ADR-008).
  2. The AuditLog port has Append(ctx, Entry) and a query method, and no update or delete method. The fake and Postgres adapter run one contract suite.
  3. Integration (testcontainers): UPDATE audit.entries … and DELETE … must fail. Enforce it in the database, not with good intentions: a BEFORE UPDATE OR DELETE trigger that raises works even for the table owner, and if you did 9.6, also revoke those privileges from the application role.
  4. Index for the real questions: by target, by actor, by time range.

E4.3 A command-level audit decorator

Goal
Record every attempt, including the denied ones, with one decorator.
Rules
AUD-4
IdRule
AUD-4An attempt that is denied by authorization is audited as denied with the actor. A failure to write the audit entry for a state-changing command fails the command (we don't change state we can't account for). For read-only queries, it degrades to a logged warning.
Your turn
  1. Write Audit[C,R](action, targetOf, next) with the same shape as E2's Require. targetOf extracts a target type and id from the command; keep it a small function per use case, written in the composition root.
  2. On success, the record goes into the context's outbox inside the use case's transaction: wrap the inner call in TxManager.WithinTx (8.4) so the repository's save and the audit record commit together. On a denial or a failure there is nothing to commit, so record the attempt in its own small transaction after the rollback.
  3. Decide and test the stack order: Audit(Observe(Require(useCase))) versus alternatives. Which order records denied attempts? Which hides them?
  4. The audit context consumes audit.records through the inbox (8.4), so redeliveries don't duplicate entries.
Pitfall

Don't serialise the whole command into the audit row "just in case". Commands can contain emails, addresses and tokens. AUD-3 says identifiers and field names. Write the test that a command with a password field leaves no password in the row.

E4.4 Attribute state changes: the actor in event metadata

Goal
Know who caused each integration event, without adding the actor to any domain event payload.
Rules
AUD-5
Touches (additively)
The outbox envelope (next to 8.3's correlation and causation ids), the consumer runner
IdRule
AUD-5When a repository writes an outbox row, it stamps the envelope with the current actor from context. Events caused by consumers carry the causing event's actor forward, with a system principal for time-triggered ones.
TDD script
  1. Saving an aggregate in a context carrying user u1 writes an outbox row whose envelope has actor=u1; the domain event payload is byte-for-byte unchanged (golden test from 5.2 still green).
  2. A consumer handling that event, then saving its own aggregate, produces outbox rows with actor=u1 and causation_id=<event id>: the consumer runner restores the actor into the context exactly as 8.3 restores the correlation id.
  3. The expiry scheduler (7.9) runs as system:scheduler.
  4. The audit consumer subscribes to the public integration topics and turns each envelope into an entry with outcome succeeded; the inbox drops duplicates.
Discuss

Why attach the actor to the envelope instead of every event's payload? Think about contract versioning (9.3) and about who owns the published language.

E4.5 Reading the trail: a protected query API

Goal
GET /audit?targetType=venue&targetId=…&from=…, for staff only.
Rules
AUD-6
IdRule
AUD-6Reading the audit trail needs audit:read, and reading it is itself audited (who looked at what).
TDD script
  1. Customer → 403; Staff → 200 with entries newest first, with keyset pagination (before=<cursor>), not OFFSET.
  2. A query writes its own audit entry (AUD-6).
  3. The response shape is a read model (as in 2.5): never expose the table row structure directly.

E4.6 Stretch: tamper evidence

Goal
Make "someone edited the table with superuser rights" detectable.
Your turn
  1. Add a prev_hash and hash column: each row's hash covers its content plus the previous row's hash (a hash chain, per target or global).
  2. Write a stagehand audit verify subcommand that walks the chain and reports the first break.
  3. Discuss what this does not protect against: a superuser can rewrite the whole chain. What would fix that (periodically anchoring the latest hash somewhere the DB admin can't edit)?
Discuss

Personal data in an immutable log collides with "right to erasure". What would you store so that deleting a person doesn't require editing the trail? (Hint: identifiers you can later unlink from the person.)
