Testing strategy & TDD

What we test at each layer, with which tools, how fast it runs, and the TDD rhythm we follow. Hexagonal architecture is what makes this pyramid cheap: the core can be tested without any infrastructure.

The TDD cycle

  1. Red: write the smallest test that describes the next bit of behaviour. Run it. Watch it fail for the right reason: a compile error counts as red, but the real goal is an assertion failure that says what's missing.
  2. Green: write the simplest code that passes. Hard-coding is allowed. The next test will force you to generalise ("triangulation").
  3. Refactor: with the tests green, clean up names, duplication and structure, in both the code and the tests. This is where the design happens. Don't skip it.
House rules
  • No production code without a failing test that demands it. (Wiring in main.go is the exception; e2e tests cover it.)
  • One reason to fail per test. Name it as a behaviour: TestVenue_Activate_FailsWithoutSections, or t.Run("rejects activation without sections", ...).
  • Test through the public API of the package. Domain tests use package domain_test (black-box), so they can't touch unexported fields.
  • Structure every test as Given / When / Then (Arrange / Act / Assert), separated by blank lines.
  • Reference the rule ID (VEN-4) in the test name or a comment.
  • Commit at green. Small commits are your undo button.

Inside-out first, then outside-in

Parts 1–5 (inside-out): start with domain unit tests, then use-case tests, then adapters. This is the best way to learn the building blocks one at a time.

Parts 6–8 (outside-in, "double loop"): write a failing acceptance test for the feature first (the outer loop, which stays red for a while). Then drive the inner loops with unit tests from the domain outward until the acceptance test goes green. This is the more professional rhythm: you never build something nobody asked for.

Level 1 — domain tests

These are the heart of the course. They're plain Go with no setup, no mocks and no I/O. Example shape:

package domain_test

func TestVenue_Activate(t *testing.T) {
	t.Run("records VenueActivated when draft venue has sections (VEN-5)", func(t *testing.T) {
		// Given
		venue := newDraftVenue(t, withSection("ORCH", rows("A", 20)))
		venue.PullEvents()                                   // discard creation events

		// When
		err := venue.Activate(fixedNow)

		// Then
		if err != nil {
			t.Fatalf("Activate() error = %v", err)
		}
		want := []sharedkernel.DomainEvent{domain.VenueActivated{VenueID: venue.ID(), At: fixedNow /* … */}}
		if diff := cmp.Diff(want, venue.PullEvents()); diff != "" {
			t.Errorf("events mismatch (-want +got):\n%s", diff)
		}
	})

	t.Run("fails without sections (VEN-5)", func(t *testing.T) { … errors.Is(err, domain.ErrVenueHasNoSections) … })
}
  • Test builders (newDraftVenue(t, opts...)) live in helpers_test.go. They hide irrelevant setup so each test only shows what matters to it.
  • Fixed times (fixedNow = time.Date(2026, 11, 1, 20, 0, 0, 0, time.UTC)) make expiry tests (TKT-4) deterministic. You never sleep in a test.
  • Assert on events and on public getters, not internals.
  • Table-driven tests for validation of value objects (many inputs, one rule).

Level 2 — application tests with fakes

Why fakes over mocks?

A mock test says "Save was called once with these arguments". That restates the implementation and breaks on every refactor. A fake test says "after RegisterVenue, the venue can be loaded and is Draft". That checks behaviour and survives refactoring. The risk of a fake is that it behaves differently from Postgres. The next section deals with that.

Repository contract tests: keeping fakes honest

We write one test suite describing what any VenueRepository must do (save then get round-trips, a missing ID gives ErrVenueNotFound, a stale version gives ErrConcurrentModification, events are drained) and run it against both the in-memory fake and the Postgres adapter.

// internal/venue/application/venuerepotest/suite.go  (exported test helper package)
func Run(t *testing.T, newRepo func(t *testing.T) application.VenueRepository) { … }

// memory adapter:   func TestMemoryRepo(t *testing.T)   { venuerepotest.Run(t, newMemoryRepo) }
// postgres adapter: func TestPostgresRepo(t *testing.T) { venuerepotest.Run(t, newPostgresRepo) } // build tag integration

If both pass the same suite, the fast application tests that use the fake can be trusted.

Level 3 — adapter integration tests

  • Build tag //go:build integration keeps them out of the default go test ./... loop, which stays under a few seconds.
  • One container per test package, started in TestMain via testcontainers-go/modules/postgres. Migrations are applied with goose (embedded FS). Starting containers per test is too slow.
  • Isolation between tests: every test uses fresh random IDs, so tests don't collide and can run with t.Parallel(). Truncate only when a test needs an empty table (e.g. the outbox relay).
  • Postgres snapshot/restore (testcontainers' Snapshot/Restore) is an option if the suite gets slow.
  • Kafka tests use testcontainers-go/modules/kafka (KRaft). If startup is slow on your machine, the Redpanda module is a Kafka-API-compatible drop-in.
  • The concurrency test for S6 lives here: 50 goroutines race to hold the last seat against real Postgres, and exactly one may win.

Contract (golden-file) tests

For each integration event in contracts, a test marshals a known value and compares it with testdata/<event_type>.golden.json. Run with -update to rewrite the golden file intentionally, and the diff then shows up in code review. This is how we spot breaking changes to the Published Language.

Architecture tests

A test in internal/archtest lists every package with golang.org/x/tools/go/packages and asserts the import rules from Chapter 3. For example: no …/domain package imports anything outside stdlib, sharedkernel and uuid; no context imports another context except its contracts. The architecture then stays true as the code grows.

End-to-end tests

  • Build tag e2e. They start the full stack (docker compose up -d --wait via the Makefile, or a testcontainers Compose stack) and talk only HTTP. They never touch the database directly.
  • Cross-context effects are eventually consistent, so they use an eventually(t, 10*time.Second, func() bool {...}) polling helper. Never time.Sleep(3*time.Second).
  • They cover the scenarios S1–S6 from Chapter 1. Keep them few: they're slow and tell you that something broke, not where.
  • Hold expiry (S2, S3) needs time control. In e2e the hold TTL is configurable through an env var (e.g. 2s), so we don't wait 10 minutes.

Make targets

make test              # go test ./...            — domain, application, http, contract, arch  (seconds)
make test-integration  # go test -tags=integration ./...   — + testcontainers                  (~1 min)
make test-e2e          # docker compose up + go test -tags=e2e ./test/e2e/...                  (~2 min)
make cover             # coverage report; we read it, we don't chase a number
Coverage

The domain will reach ~100% coverage naturally with TDD. Don't chase a percentage elsewhere. One good e2e test covers main.go wiring better than an artificial unit test would.
