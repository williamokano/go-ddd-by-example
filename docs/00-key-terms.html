Key terms in ten minutes

Every term the course uses, in one or two sentences each, with a Stagehand example. Read this once now. When a word in a lesson feels fuzzy, come back here, then follow the link to the chapter that covers it in depth.

First: "driving" and "driven"

Hexagonal architecture splits the world outside your application into two sides. The names we use for them are driving and driven. Alistair Cockburn, who invented the pattern, chose them, and they appear in folder names throughout this repo (adapters/driving/…, adapters/driven/…).

Driving side

Things that drive (use) our application. They start the conversation: they call us. Our application is passive here and waits to be asked. Examples: a customer's HTTP request, a Kafka message from another context, a timer that ticks, a test.

Driven side

Things our application drives (uses). We start the conversation: we call them. They wait to be asked. Examples: Postgres, the Kafka producer, the payment provider, the system clock.

One question decides it: who calls first?

Think of a car. The driver drives the car: they start every interaction by turning the wheel or pressing a pedal. The car in turn drives its wheels, which only ever react to the car. Our application is the car: users and messages are drivers, and databases and payment providers are wheels.

It isn't about which way the data flows. GET /venues/{id} sends data out to the user, but the user called first, so it's driving. repository.Get(id) brings data in, but we called first, so it's driven.

Ports and adapters

Port
An entry or exit point of the application, defined in the application's own language. In Go, it's a set of types and methods: a use case's command plus its Handle method, or an interface such as VenueRepository. A port knows nothing about HTTP, SQL or Kafka. Think of it as a socket in the wall.
Adapter
A piece of code that connects one technology to a port, translating in both directions. Think of it as the plug that fits the socket. You can swap the Postgres plug for an in-memory plug and the application doesn't notice.

Combine the two words and you get the four terms used everywhere in the course:

TermWhat it isWho owns the definitionStagehand example
Driving portWhat the application offers: its use casesThe applicationRegisterVenueHandler.Handle(ctx, RegisterVenue)
Driving adapterTurns an outside protocol into a call to a driving port—HTTP handler, Kafka consumer, hold-expiry scheduler
Driven portWhat the application needs: an interface it declaresThe applicationVenueRepository, PaymentGateway, Clock
Driven adapterImplements a driven port with a real technology—Postgres repository, fake payment gateway, system clock

Note the "who owns" column. The application defines both kinds of port. Adapters always depend on the application, never the other way round. That's the dependency rule.

The same ideas under other names

You'll meet these in books, blog posts and other codebases. They mean the same thing:

We sayAlso calledWhere you'll see it
Drivingprimary · inbound · in · input · user-side · left sideCockburn uses "primary" too. "In/out ports" (port/in) comes from Tom Hombergs' Get Your Hands Dirty on Clean Architecture, popular in Java codebases.
Drivensecondary · outbound · out · output · SPI · server-side · right sideThe same sources. Clean Architecture calls driven ports "gateway interfaces".
Driving portuse case · input port · application APIClean Architecture: "input boundary".
Driven portoutput port · secondary port · gatewayClean Architecture: "output boundary".

Why we use driving/driven: "in/out" and "inbound/outbound" are fine once you define them by who calls first. Read literally, though, they suggest a data direction, and the GET example above shows how that misleads. "Driving/driven" carries the right meaning in the word itself. Strategic DDD: the big picture

Domain
The business area the software serves. Here, selling tickets for live shows.
Domain expert
The people who know the business: venue managers, promoters, box office staff. Our code should speak their language.
Ubiquitous language
The shared vocabulary between experts and developers, used everywhere, including in type and method names. Example: we say hold seats, never reserve or lock. More →
Subdomain
A part of the business problem. Core: what makes us win (Ticketing). Supporting: needed and specific to us (Venue, Show). Generic: everyone needs it, so buy it (Payments, Notifications). More →
Bounded context
A boundary in the solution inside which each word has exactly one meaning and one model applies. In Stagehand: Venue Management, Show Scheduling, Ticketing, Notifications. In code, one tree under internal/.
Context map
A diagram of how the bounded contexts relate and integrate.
Upstream / downstream
Upstream changes flow down to whoever depends on them. Venue is upstream of Show, and Show is downstream of Venue.
Published Language (PL) / Open Host Service (OHS)
A context's documented, versioned public protocol, separate from its internal model. Ours: the integration events in internal/<ctx>/contracts.
Anti-Corruption Layer (ACL)
A translation layer on the downstream side that converts a foreign model into our own, so upstream changes can't leak into our domain. Example: Show turning venue.activated.v1 into its own VenueLayout.
Conformist
A downstream context that simply adopts the upstream's model as it is. Notifications does this.
Shared kernel
A small piece of domain model that several contexts share and change only together. Ours: Money, Currency and the domain-event building block. It's not a "utils" package. More →
Event storming
A workshop where you put domain events on sticky notes along a timeline to discover the domain and its boundaries. Lesson 0.1.

Tactical DDD: the building blocks

Value object

An object defined only by its values. It has no identity: two Money{1500, EUR} are interchangeable, just as two €10 notes are. It has three properties:

  • Immutable. You never change one. You make a new one (a.Add(b) returns a new Money).
  • Always valid. Its constructor rejects bad input, so if you hold one, it's valid.
  • Equal by value. Same fields means same thing (== in Go).

Most of a good model is value objects. Stagehand's include VenueID, Address, SectionCode, Row, Schedule, Money, PriceList, SeatRef, OrderLine and TicketCode. You'll write your first one in lesson 1.1. More →

Entity
An object with an identity that stays the same while its data changes. A Section is still "ORCH" after it's renamed, and a Hold is a specific hold even if another one covers the same seats. More →
Invariant
A business rule that must always hold. Example: "a seat is never sold twice" (TKT-5).
Aggregate
A cluster of entities and value objects that must stay consistent together. It's the boundary inside which invariants are enforced immediately, and it's saved and loaded as one unit. More →
Aggregate root
The one entity of an aggregate that the outside world may touch. All changes go through its methods, so it can check the invariants that span the cluster. Venue is the root, and nobody outside edits a Section directly.
Domain event
A fact that happened and that the business cares about, in the past tense: SeatsHeld, ShowCancelled. The aggregate records it, and it's published later. More →
Domain service
Business logic that doesn't belong to any single entity, usually because it spans several aggregates. It's stateless and pure. Examples: SchedulingPolicy (no two shows overlap at a venue), ShowSoldOut (9.1: is every section sold out?), PricingPolicy (9.8: fees and VAT). More →
Specification
A small predicate object (IsSatisfiedBy(x) bool) that can be combined with And, Or, Not, so a business rule reads as a sentence instead of an if-else chain. Example (9.8): the group fee applies when SeatsAtLeast(6).
Application service / use case
The coordinator for one user intention: parse input, load, call the domain, save. It contains no business rules. Example: PublishShowHandler. More →
Command / query
A command asks to change something (HoldSeats). A query asks for data and changes nothing (GetVenue). We handle them on separate paths: "CQRS-lite".
Repository
A driven port for loading and saving whole aggregates, one per aggregate root, not one per table. More →
Factory / reconstitution
Creating an aggregate (RegisterVenue: validates and records an event) is different from rebuilding one from the database (RehydrateVenue: no validation, no events). More →
Read model / projection
Data shaped for reading, often built from events. Example: Show's local VenueLayout table.
Policy
"Whenever X happens, do Y." Example: whenever a venue retires, cancel its future shows.
Saga / process manager
A multi-step business process across aggregates or contexts, driven by events, with compensating actions if a later step fails. Example: checkout, which refunds if the seats couldn't be confirmed. Choreographed (each step reacts to the last) or orchestrated (a stateful CheckoutProcess decides the next step, 9.4). More →
Anemic domain model
The anti-pattern: entities that are bags of getters and setters, with all the rules in services. We avoid it.

Architecture terms

Hexagonal architecture (ports & adapters)
The business core in the middle, with every technology plugged in through ports and adapters. Onion and Clean Architecture are the same idea. More →
Dependency rule
Source-code dependencies point inward: adapters → application → domain. The domain imports nothing from the outer layers.
domain layer
Business rules only: value objects, entities, aggregates, domain events, domain services. Pure Go, no I/O.
application layer
Use cases plus the port definitions. It orchestrates, and owns transactions and authorisation.
adapters
adapters/driving/… (HTTP, consumers, scheduler) and adapters/driven/… (Postgres, payment, memory fakes).
contracts
A context's public integration-event types (its Published Language). It's the only package another context may import.
platform
Technical plumbing shared by everyone: DB pool, Kafka client, outbox relay, HTTP helpers, config. No business logic.
Composition root
cmd/stagehand/main.go, the only place that creates concrete types and wires them together.
Modular monolith
One deployable binary with strictly separated modules (our bounded contexts) that talk as if they were separate services.

Messaging terms

Integration event
The public, versioned version of a domain event, meant for other contexts (show.published.v1). More →
Dual-write problem
Writing to the database and to Kafka can't be atomic, so one of the two can be lost.
Transactional outbox
The fix: write events to an outbox table in the same DB transaction as the aggregate. A relay then publishes them to Kafka.
At-least-once delivery
Every message arrives, maybe more than once.
Idempotent
Doing it twice has the same effect as doing it once. Consumers must be idempotent.
Inbox
A table recording processed message IDs so duplicates can be skipped.
Consumer group
Kafka's way of letting each context read every message independently.
DLQ (dead-letter queue)
Where messages that keep failing are parked, so they don't block everything else.
Eventual consistency
Other contexts catch up shortly after, not instantly. Example: the show becomes SoldOut a moment after the last ticket sells.

Testing terms

TDD (red → green → refactor)
Write a failing test, make it pass in the simplest way, then clean up. Repeat. More →
Test pyramid
Many fast domain tests, fewer use-case tests, fewer adapter integration tests, and a handful of end-to-end tests.
Test doubles
Fake: a working lightweight implementation, such as an in-memory repo. This is our default. Stub: returns canned answers. Spy: records calls. Mock: pre-programmed expectations, which we avoid.
Contract test
One test suite run against several implementations of a port (memory and Postgres), so the fake stays honest. Also, golden-file tests that freeze an integration event's JSON shape.
Testcontainers
A library that starts real Postgres or Kafka in Docker from inside a Go test.
Acceptance / end-to-end test
Tests a whole scenario from the outside, over HTTP, against the running stack.
Double-loop TDD (outside-in)
Start a feature with a failing acceptance test (outer loop), then drive the implementation with unit tests (inner loops) until it passes. We switch to it from Part 6.
